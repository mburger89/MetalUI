# 350 - Terminal ConPTY, `PseudoTerminal` on Windows (`TRM-AX`, `TRM-AY`)

Renumbered from 348 because #350 and #351 merged first (#352 holds 349). Branch `feat/terminal-conpty`, merged with master `49630aaf`; Phase 2.3 of `docs/superpowers/plans/2026-11-16-terminal.md`. Class M, no divergence label. Ids `TRM-AX`, `TRM-AY` (after `TRM-AW`).

**What landed.** The frozen `PseudoTerminal` API on Windows, no API change: `spawn`, `processID`, `onReadable`, `read`, `write`, `resize`, `signalGroup`, `foregroundProcessGroup` (always nil), `exitStatus`, `close`. The engine is C (`Sources/CPseudoTerminal/CPseudoTerminalWindows.c`, `cpw_*`, under `_WIN32`) and `PseudoTerminal+Windows.swift` is a thin Swift core around it; the POSIX file is unchanged apart from `Signal`, `ExitStatus` and `PseudoTerminalError` moving to `PseudoTerminalTypes.swift` (shared). Why C: `STARTUPINFOEX`, attribute lists, overlapped structures and a thread-pool callback are all plain in C and awkward through WinSDK (the `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` macro does not even import).

**The design** (full text `TRM-AX`, `TRM-AY`). Overlapped named pipes with unique names; the child suspended, put into a kill-on-close job, then resumed; no handle inherited; one `CreateThreadpoolIo` per direction and a registered wait for the exit, so no thread per pty. Reads land in a 256 KB ring with back pressure; writes are an ordered overlapped chunk list. `.interrupt` writes 0x03, every other signal is `TerminateJobObject` (`.exited(1)`).

**Close and drain.** `ClosePseudoConsole` can block until its output is read, so it only ever runs on a short-lived closer thread while the thread-pool read loop keeps going (buffering until the child ends, discarding once `close()` was called). The child's exit starts the same closer, because conhost holds the output pipe open until the console is closed; that is what makes the stream end after the last byte. `close()` runs a teardown on one more short-lived thread (job closed first, so everything ends; then closer, read loop, process, wait, IOs, handles) and reports whether every step finished in time through `package func waitUntilReleased(timeout:)`, which the tests use to prove nothing deadlocked. No callback reaches the caller's queue after `close()`.

**Also.** `WindowsCommandLine` (`CommandLineToArgvW` quoting, sorted UTF-16 environment block) and `DefaultShell` (`pwsh`, then `powershell`, then `%ComSpec%`; POSIX `$SHELL` or `/bin/sh`) are pure `package` functions, tested on every platform; the Windows file also round-trips thirteen argument lists through the OS's own `CommandLineToArgvW`.

**Tests.** `WindowsCommandLineTests` (every platform: quoting rows, program-name rule, environment block, resolver order with a fake `PATH`, quoted and slashed entries). `PseudoTerminalWindowsTests` (Windows only; every wait bounded, no sleep for timing, judged on the emulated screen): `cmd /c echo` and the stream ending, `powershell` output, environment and cwd, missing program (2) and directory (267), initial size and resize (`$Host.UI.RawUI.WindowSize`), `exit 7`, terminate/kill/hangup `.exited(1)`, a grandchild `ping` ended by `.kill` and by `close()` (verified through its process handle), no-op after exit, `.interrupt` ending `ping` with `0xC000013A`, no foreground group, ordered writes, a 1 MB write that does not block, no callback after `close()` during a `for /l` flood, close with an unread flood not deadlocking, idempotent close. `DefaultShellOnDiskTests` runs the resolver against real files on a temp `PATH`.

**Where it was checked.** macOS: `swift build --build-system native --build-tests` and the `MetalUITerminalTests` run, 218 tests green (was 183; the new ones are the pure `WindowsCommandLineTests`). Two mutations in `WindowsCommandLine` (trailing-backslash doubling, resolver order) each went red and were restored. The C file compiles clean with `-Wall -Wextra` against mingw-w64 headers (a `swift:`-less `debian:bookworm-slim` container with `gcc-mingw-w64-x86-64`, removed afterwards). The Windows Swift code and the Windows tests could **not** be run locally: the UTM VM was stopped and `utmctl start` and `utm://start` did not bring it up from a CLI session; CI's "Root package (Windows x64)" is their first run.
