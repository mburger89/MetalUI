Branch `feat/text-editor-caret` (origin/master `7ac6e929`). Rulings `SL-P`, `SL-Q` in `docs/superpowers/2026-10-12-text-selection-decisions.md` (next `SL-R`) and `CB-S` in `docs/superpowers/2026-10-14-clipboard-types-decisions.md` (next `CB-T`). No divergence added (the live count and next label are unchanged): the caret rule matches measured SwiftUI, `selectedOffsets:` is class `M`, and the paste order is MetalUI's own rule, SwiftUI's not being measurable headlessly. Human checks group `EC` (not run).

## 1. What was asked and built

1. **The caret bug.** A focused `TextEditor`/`TextField` whose bound text was replaced from code (autocomplete "/com" -> "/compact ", an `@path` appended) kept the old caret offset, so the next key landed mid-text. SwiftUI measured first (`docs/probes/swiftui-text-external-replace.swift`, macOS 27.0.1, Swift 6.4, compiled, one arm per process, run twice, byte-identical outputs, 36 arms): `TextField` and `TextEditor` agree on every row: after any change the typed key lands at the **end** of the new text, and only identical text keeps the caret. It is neither "clamp the old offset" (shrink inside the kept text goes to the end) nor "end only when the edit is not at the caret" (extending at the caret also goes to the end, even `ab|cd` -> `abXY cd` lands after the whole text). With a selection binding attached the old offset stays, clamped (`/com`@4 -> `/comXpact `, `abXXY cd`, `helX`). Built: `TextEditState.seenText` (set by every own edit, undo and redo; otherwise by the frame) and `TextEditing.followExternalText`, called from `TextEditor.prepaint`/`TextField.prepaint` inside the compared `withState` that `reconcile` already uses (that site's `if selectionWriter != nil` became `if bound ... else follow`; `everyStateWriteSiteIsClassified` is unmoved). Focused fields only; an unfocused one forgets the text (`SL-P`).
2. **G11, the selection binding on macOS 14.** The `#available(macOS 15, *)` in `reconcile` is not removable: `TextSelection` is `@available(macOS 15, *)` itself (`RangeSet`, `SL-L`; SwiftUI's is macOS 15 too) and the package deploys to macOS 14. So the MetalUI-only `TextField(_:text:selectedOffsets:)` and `TextEditor(_:text:selectedOffsets:)` over `Binding<Range<Int>?>` (Character offsets, empty is the caret) were added (`SL-Q`); `reconcile` tries the `Range<Int>` cast first, with no availability question, and `TextSelection` behind the gate second. Everything else (`SL-B`..`SL-J`) is shared. An insertion at the caret is the app editing `text` and writing the caret after it.
3. **G10, image paste.** `Window.offerPasteToDestinationBeforeTheField` (in `ClipboardModifiers.swift`; `Clipboard.swift` is untouched, so the `feat/env-clipboard` branch's edits do not meet it) walks the focus chain as `dispatchClipboardKey`'s paste does and is called at the top of `dispatchTextKey`: an accepting destination consumes the key, a declining or absent one leaves the field to paste text (`CB-S`).

## 2. Findings along the way

- **The probe's rows are uniform** where the Alloy brief hedged ("moves to the end when the new text isn't a simple edit at the caret"): there is no simple-edit exception. The brief's reading would have left `/com` -> `/compact ` alone, which is the very case reported.
- **A phase write on every unbound field was the first design, and a pinned test found it.** Writing the `seenText` baseline for an unfocused field left a non-fresh `TextEditState` behind a field that left the tree and returned (`aFocusedTextFieldInsideAToggledIfLosesFocusAndStartsFresh`), and a stale `seenText` would have turned the click that focuses a field into a "replacement" and overridden the clicked caret. Hence focus-gating with a reset (`SL-P`).
- **`PrepaintPass.isFocused` is paint-only by a guard** (`queryingFocusDuringPrepaintDoesNotCompile`); prepaint reads `pass.frame.focusedElement`, the pre-clearing answer, which is enough here.
- **`CB-M`'s pin moved.** `aFocusedTextFieldKeepsItsOwnCopyCutPasteUnderACopyableAncestor` (1.8) had an ancestor `pasteDestination(for: Graph.self)`, and `Graph` imports the text type too: under `CB-S` that destination takes a text clipboard. The test now uses a destination for `Blob`, which declines. A migration note says so.
- A binding that rejects or transforms every edit (`.constant`) now counts as a replacement: after a typed key the caret goes to the end rather than advancing one. (SwiftUI does the same: the field's text is set from outside.)
- The `TextEditor` focus default (caret at the end in SwiftUI, at the start of a fresh MetalUI state) is divergence 265/266's, not touched.

## 3. Tests

`Tests/MetalUITestingTests/ExternalTextCaretTests.swift` (7 tests, 66 cases) and `PasteDestinationBeforeFieldTests.swift` (6 tests, 10 cases), portable (plain imports, `harnessTextSystem`); `ClipboardTypesTests` 1.8 amended. For G11: the offsets binding reads and writes the caret and the selection (typing, a caret write, a range write, a stale range, select-all) and `theOffsetsInitialisersCarryNoAvailabilityGate` reads the sources (the harness cannot run macOS 14; an `@available(macOS 15, *)` on an initialiser also fails the build of the tests). For G10: image-only (a `Blob`, then a real PNG `ImageData`) on the editor itself, on a container and on a field; a text clipboard with a non-matching destination; a clipboard with both; a declining validator; no destination.
