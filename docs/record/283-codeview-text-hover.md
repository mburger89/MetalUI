# 283 - CodeView text hover (Alloy G35 F, `CV-AS`)

Branch `feat/codeview-text-hover` from master `ec3940d2` (after G35 A, B, D and E, records 270, 281, 272, 282). Class `M`, no divergence added or retired.

**What.** Alloy's LSP client shows a hover popover after the pointer rests on a symbol. `CodeView.onTextHover(delay: = .milliseconds(500), perform:)` reports `CodeHoverPhase` (`.active(CodeHit)` once after the rest, `.moved(CodeHit)` at once when the pointer moves onto other text while active, `.ended`), and holds `.ended` for a 150 ms grace while a text-anchored popover (record 282) of the same view is open, so the pointer can travel into the popover and stay in it (Alloy answer 1).

**How.** `CodeHoverTrack` in `CodeViewState`; a runtime object built in prepaint only for a view with a handler registers the view's continuous hover, is held by the wheel closure and the edit session (a press, a key, typed text and a composition end a hover) and by the per-build `CodeTextAnchorBox`, which the wrapper fills with whether the popover is presented and whose chrome carries a hover attachment that reports the pointer entering and leaving the panel. The delay and the grace are `TimelineStore.noteDeadline` deadlines (`CV-AC`): input writes the phase with no timer, the next prepaint stamps it with the frame time and notes the deadline, the frame at or after it enqueues the callback through the lifecycle queue (`CV-T`). One wake, one frame; no display link.

**Plan points that changed against the code.** (1) The timer start is stamped by the first prepaint after the input, not by input: a hover callback carries no clock the frames share. (2) The grace needs the popover's panel: the plan's per-build box would mismatch the closures a retained replay keeps, so every phase that holds one calls `taintRetention`; it turned out defensive (a hovered view and a host that holds a presentation are ineligible already), and the test says so rather than claiming a mutation. (3) An end by a press left the next hover refresh to fire a second `.active` on the same word: an ended hover remembers its grapheme and does not restart there until the pointer is on another grapheme or off the text. (4) Escape and an outside press reach the view through the wrapper's `dismiss`, not through the session (an open `.popover` takes Escape first, `CV-AR`), so the text-anchored overloads' dismissal also ends the hover. (5) A key the app's `onKeyPress` handles does not reach the session and does not end a hover; documented. (6) The app's own `onContinuousHover` is never dropped: `HoverAttachment` gained `localContinuous`, always called with local points beside the app's callback in its own space (pinned by `anAppsGlobalContinuousHoverStillRunsBesideTheTextHover`).

**Tests** (`Tests/MetalUITestingTests/CodeViewTextHoverTests.swift`, mutations run once each): `aRestFiresActiveOnceAfterTheDelayFromOneWakeWithoutTheLink` (`noteActiveAnimation` for the deadline: red), `movingRestartsTheDelayAndReportsMovedImmediately` (timer not restarted: red), `typingAPressAndTheWheelEndTheHover` (the end removed from key, press and wheel: red each; from `insert` alone it stays green because a typed character also arrives as a key), `noHoverHandlerNoStateWrites` (hover installed without a handler: red), `retainedVerifyStaysGreenWithAPendingHover` (green under `METALUI_VERIFY_RETAINED=1`; the taint is defensive), `leavingIntoTheOpenPopoverWithinTheGraceKeepsTheHover` (`panel(_:)` ignored: red), `leavingWithNoPopoverEndsImmediately` (grace applied without a popover: red), `graceExpiresOutsideBothEnds` (the grace deadline not noted: red); the last two grace tests are the end-to-end ones with the record 282 popover, opened on `.active` and closed on `.ended` as Alloy does. `everyStateWriteSiteIsClassified` gains the row for `Code/CodeTextHover.swift` (1 plain, 1 read); `Window.testingStatePlainWriteCount` is the test hook.
