# 324 - A split view's dividers are accessibility elements (`HS-K`)

Branch `feat/split-divider-ax` from master `f9e2af33`. Alloy found that MetalUI's dividers are not AX elements (a screen reader cannot find or move them). Ruling `HS-K` in `docs/superpowers/2026-10-30-split-view-decisions.md`; the identifier modifier is class M; divergence 206 is amended, no label added.

**Probe** `docs/probes/swiftui-split-divider-ax.swift` (macOS 27.2.1, in-process, no computer use). SwiftUI's split view is an `NSSplitView`; each divider is an `NSSplitViewSplitter` (`NSAccessibilityElement`): `AXSplitter`, role description "splitter", orientation 1 for a vertical line (HSplitView) and 2 for a horizontal one, value the size in points of the pane before it (133 and 132 for 133 | 132 | 133), min 0, max the pair's sum (265), settable (a write moves the divider like a drag: 150 gave 150 | 115 | 133; 0 clamps to the pane's minimum, 50; 1000 is ignored), NO actions (the inherited `accessibilityPerformIncrement` raises "unrecognized selector"), no label, identifier or help, and `.accessibilityIdentifier` on the split or a pane never reaches it. Unmeasurable: what VoiceOver's keyboard resize sends (human check HS1).

**What landed.** `AccessibilityRole.splitter`, `AccessibilityOrientation`, `AccessibilityActions.setValue`, `AccessibilityNode.numericRange`/`orientation`, `AccessibilityRequest.setValue(id, Double)` (platform tree); `AXRoleHint.splitter` (a case on the existing optional enum, 1 byte, so `AXNode` and `Handlers` keep their pinned sizes) and the internal `SplitterAccessibility` action (query / set) the divider registers; the builder asks it at step 3 for value, total, orientation and mobility; `Window` sends the set through the divider's handler under `StateDispatch`; the handler is `SplitSolver.dragged` from the layout's last report, so min and max sizes hold, and writes the autosave once and only on a change. `SplitSolver.movableRange` (factored from `dragged`). AppKit: `AXSplitter`, `AXOrientation`, numeric `AXValue`, `AXMinValue`, `AXMaxValue`, settable `AXValue` only where `.setValue` is advertised. AccessKit 0.23 has `SPLITTER`: role, `orientation`, numeric value and range, `SET_VALUE` (numeric action data). Harness: `TestWindow.setAccessibilityValue(_:on:)`.

**Identifier approach.** SwiftUI has none, so MetalUI-only `splitViewDividerIdentifier(_ prefix:)` on both split views: divider *i* is `prefix.i`; nothing by default.

**Decisions.** No increment or decrement (the probe: none). The element is the 6-point hit area, published after the panes; an immovable or disabled divider is disabled with no actions. Divergence 206 records these.

**Tests** (each failed under its mutation): `SplitDividerAccessibilityTests` (portable harness; role, value, range, orientation, order; VSplit horizontal; no increment; set = drag; clamps and ignored beyond the total; autosave once; immovable and disabled; identifiers; record 310's nest), `SplitDividerAppKitAccessibilityTests` (the AppKit attributes, the request, disabled), `AccessKitSplitterTests` (SDL package, `--print-flags` flags). Mutations run: orientation inverted, autosave write dropped and `canMove` always true together (nine expectations red across six tests); `.increment` added to a splitter (`aSplitterHasNoIncrementOrDecrement`); AppKit role mapped to `.group` and the setter's request dropped (four red); AccessKit max range and set-value number replaced (five red). The role-hint mapping itself was not mutated alone: every portable test finds its element by role.

**Behaviour, not API changes** except the additions above; the new enum cases and request are a migration note for an exhaustive `switch` over `AccessibilityRole` or `AccessibilityRequest` outside this package.
