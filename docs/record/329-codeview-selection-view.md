# 329 - The view lane of per-view CodeView selections: `CodeView.selectionState(_:)` (`CV-AY`, `CV-AZ`)

Branch `feat/codeview-selection-view` from master `f7badefc`. Lane 3 of the work designed in `docs/superpowers/specs/2026-11-16-codeview-selection-state-design.md` (probes: record 325; buffer lane: record 327). Class M, no divergence. SwiftUI was checked in record 325 (its `TextEditor(text:selection:)` does not move a bound selection on an external change), so the AppKit/Xcode behaviour needs none.

**What landed.** `CodeView.selectionState(_ state: CodeSelectionState) -> CodeView` (precondition `state.buffer === buffer`), and inside the view `selectionSource = state ?? buffer.selectionState` for everything: the plan's selection and head (observed per state, so a caret move in A wakes A and not B), the reveal (the source's `revealSerial` plus `CodeViewState.revealSource`, the source's identity, so swapping a view's state reveals nothing), caret-into-view after a key (the editing view's own `revealsCaret`), every `CodeEditSession` command (press, drag, `endDrag`, moves, select all, delete, cut, paste, newline, indent/outdent, undo/redo) through the state's methods so it is the acting state, find (`state.select(match, reveal: true)` centres only that state's views), copy, the caret rectangle, the IME area and `CodeTextAnchor.caret` (all from the plan), and the blink (unchanged). Marked text (`CV-AZ`): the composition stays the view's, at its own state's caret; **any edit made through another state ends it and commits the composed text through the composing view's own state**, at that state's caret as the edit left it. Mechanism: a view registers a handler on its state when marked text starts (`CodeSelectionState.foreignEditHandlers`, `package`, `@ObservationIgnored`, empty unless an input method composes); `CodeBuffer.asActing` runs the handlers of every other state once, after the **outermost** edit made through a state's API completes (not mid-transaction). The demo has an "Own carets" button (`METALUI_CODE_DEMO=1`, built only, not launched) that gives the main and side views a state each. Rulings `CV-AY` (view wiring) and `CV-AZ` (landed) in `2026-11-07-code-view-decisions.md`; `CV-P`, `CV-V`, `CV-AE`, `CV-I`, `CV-D`, `CV-F` amended; next unused `CV-BA`. Human check `CV22`.

**Steady-frame cost (binding rule).** `selectionState(_:)` adds no element, wrapper or request; a view without it reads `buffer.selectionState` (a lazy `@ObservationIgnored` property, the same state the buffer's selection API forwards to, observed through the same `selections` access as before). Literals, measured on master f7badefc with a retained card per view beside a focusable box (`steady(views:states:)`): one view 4 element requests, 0 retained hits, 1 miss, 0 ineligible; two views 5 / 1 / 1 / 0; with a state per view the same. A caret move (right arrow) in A: with a state each, the retained card of B hits and only A's misses (1 hit, 1 miss); sharing the default state both miss (0 / 2).

**Conflicts and limits found.**
- The handler for another view's edit is reachable only through edits made through a *state* (a view's session, `state.replace`, `buffer.replace`, undo). An external edit (`applyExternalEdits`) is not "by another view": it keeps the old rule (the composition's offset mapped through the log, or dropped). A programmatic `buffer.replace` runs as the default state, so it ends the composition of a view with a state of its own; two views sharing a state (the default one) do not end each other's. A focus change still drops a composition with no commit (`IM-I`), so from the keyboard the case is "another view's state edited while this view still has the input method".
- The platform's own marked-text bookkeeping is not told when a foreign edit commits it (the harness's `markedText` reads the view's state, which is cleared).
- The `CodeView` copy handler (`copyingSelection`) now reads the state, but `typeKey(⌘C)` in the harness reaches the text stage before the clipboard attachment, so no test can tell the handler's source apart (a mutation of it survives; the session's copy, which does read the state, is pinned).

**Tests** (`Tests/MetalUITestingTests/CodeViewSelectionStateTests.swift`, 12): two views keep their own carets; typing in A moves B's caret and not B's scroll; a view without a state follows the buffer; reveal per state; swapping a view's state reveals nothing; copy, cut and paste use the focused view's selection (an empty selection copies its line, not another state's range); find steps and centres only in the stepping view; undo in the other view brings its caret to the change (`CV-AX`); marked text in B is committed and ended by an edit in A, away from and at the mark; the caret rectangle follows the view's state; A's arrow key does not replan B; the steady-frame literals. `revealCentresTheLineInEveryViewOfTheBuffer` and every other existing test pass unchanged. **Mutations**, each turning the suite red: the press writing `buffer.selections`; the caret reveal forced on every frame; the reveal serial from the buffer; no reveal-source comparison; find through `buffer.select`; undo through `buffer.undo()`; the foreign-edit handler not registered; the plan reading `buffer.primarySelection`; the source a fresh state; the source ignoring the view's state (ten tests red).
