# 295. A closed code-driven menu no longer taints the graft (`RW-V`)

Renumbered 292 to 295 at its merge with `master` (record 292 is `292-three-clipped-islands.md`, published first). Branch `fix/retained-presentation-taint` (master `de44a640`). Ruling `RW-V`. Class `M`; no public API, no divergence.
Source: Alloy G33(a) A0 follow-ups, from `METALUI_TRACE_RETAINED=1` traces of 20 keys typed into a `CodeView`.

## What the traces showed, and what was already there

1. **Counters.** `FrameWork.retainedRedos` and `retainedBackoffFrames` (documented, summed, carried from the window's `RetainedCounters`) already exist since `RK-D` item 4 and are pinned (`RetainedPrepaintTests`, `RedoCounterTests`); nothing to add. The `FRAMEWORK` line of the trace is Alloy's own test print (`ViewRerunTests`), which can print them.
2. **"because presentation"** (graft-ineligible, 117 decisions). A plain `Menu` and a menu-style `Picker` do **not** taint (1 graft, 0 requests). The cause is `Menu(...).menuPresented(binding)` (Alloy's `/model` opener, G9): the closed menu still noted a `PresentationRecord`, which the graft journal could not replay. A bug against `RW-K`'s intent: `RW-V` (generalised to a closed `.alert`, dialog and `fileImporter` scope, which noted the same record).
3. **"because presentation" through ancestors, and "because dragAndDrop" (Alloy G45: the composer split into a drop-destination shell and `.equatable()` leaves, presentation 129 to 162, dragAndDrop 97, 132 requests).** Confirmed with file and line: the graft taint is `BuildAudit.movedChannel` (`RetainedGraft.swift:108`), a count compared over the enclosing window, so a presentation record anywhere in the range moved it; the prepaint taint is `RetainedPrepaint.swift:495-497` in `closePrepaintWindow`, `hitboxes(from: recorder.hitboxLow)` over the enclosing window's range, so a drop-destination hitbox registered by any nested occurrence taints every ancestor. The presentation half is fixed for **closed** scopes of every kind (menu, alert, dialog, file dialog) by `RW-V`, and composes through nesting because the journal is shared by every open window and a grafted nested occurrence replays its journal through `reapply` into the enclosing ones (measured on a root over a retained column holding a card, a chat card and the composer: 19 element requests per steady frame before, 2 after). The drop half does **not** compose by scoping alone: an occurrence with a drop destination has no ledger (it is the tainted one), and an ancestor's replay hides it, so its hitbox, and the `handlers.dropDestination` closure with it, would have to ride in the ancestor's ledger. That is full ledger replay of drop hitboxes (`RetainedPrepaint.swift:495-497` removed for destinations, hover/targeting state `isTargeted`, the drag session's `dragSnapshot` and preview, `hasDraggable` capture primitives): **not implemented, design reported to the coordinator**. Earlier note, superseded: Prepaint "because dragAndDrop" (88) is `ComposerView`'s `.dropDestination` and is **not** changed (out of scope, high risk). It also means `ComposerView`'s own ancestors cannot graft until it is replayable: a graft needs a prepaint ledger (`graftRecord(for:)`), and a drop destination leaves none. The menu fix is the part that was a bug; it recovers the grafts of every composer-shaped occurrence **without** a drop destination.
4. **The nine-build suspension** after one redo (`RK-D` item 3): measured (three cards, one under a changed ambient: element requests 86 x 9 then 2, prepaint hits 0 x 9 then 3) and a scoped suspension (only under the occurrences that requested the redo: 86, then 30 x 8) built and verified green under `METALUI_VERIFY_RETAINED=1`, then **dropped**: Alloy cannot reproduce the redo (it removed the late title-bar-inset dependence, its steady frame is 132 requests), so it had no measured app benefit and it adds a cost case (a second independent ambient change inside the nine builds pays its own redo). `RK-D` item 3 stands.
5. **Title-bar insets applied a frame late (Coordinator's hint).** By design, not a MetalUI lag that can be removed: `.windowTitleBarMetrics(...)` is *collected from the build* (`Frame.collectedTitleBarMetrics`), `adoptShellPreferences` sends it to the platform after the build (`reconcileTitleBarMetrics`, `AS-R`) and redraws, because the platform's `titleBarInsets` answer depends on what the tree declared. The first build can only use the platform's default insets; knowing the metrics before the first build would need the app to declare them outside the tree. Left as is; a redo is the wrong tool for it, the scoped backoff is what bounds its cost.
