# 438: a padding and an accessibility identifier written on a `ProposalScrollView` cost nothing, and an indicator margin moves the thumb across its axis (`SP-M`, `SP-N`, `SP-O`, `CMG-G`; class A, divergence 250)

Branch `feat/scrollview-inset`, base master `eb25ea24`. Public API: `padding(_:)` (four spellings) and `accessibilityIdentifier(_:)` on `ProposalScrollView` and on the plain flex `ScrollView`; 243 live divergences (250 added), next label 251.

**Why.** Alloy insets its transcript scroller horizontally (x 266..828 to 273..817) so the viewport's corners are clear of a `.clipShape(RoundedRectangle(cornerRadius: 10))`, and the inset cost +3 element requests per streamed delta (117.2 to 120.2). Two came from writing `VStack { ScrollViewReader { ScrollView { ... } } }.padding(.horizontal, 7)` (the `VStack` and the padding wrapper), one from `.accessibilityElement(children: .contain)` around the scroller to keep an identifier from overwriting the rows' `block-*` ids. After the inset the thumb (`maxX - 5`, 3 wide) touched the rows' right edge.

**Gap 1 (`SP-M`).** `.padding` already compiled on a `ProposalScrollView` (it is a `ProposalElement`), through `ProposalElementGroup`'s `ModifiedContent` wrapper: measured +1 element request over the bare scroller on the fixture, +2 in the wrapped form. The scroller now takes the padding itself: four concrete `padding` members store an `Edges<Pixels>` (a second padding adds) and `requestProposalLayout` registers one native padding node around the viewport, `Layout.viewportNode` being the viewport and `Layout.node` the registered node; `prepaint` and `paint` read the viewport's bounds from the layout when the two differ, so the scroll region, the clips and the thumb are the inset rectangle's. No element, no identity level. The transcript fixture (40 lazy rows, bottom anchor, a delta into the last row): **38 requests bare, 38 padded directly, 40 wrapped**, steady and per delta. Row frames, the bottom anchor, a wheel to the top and `scrollTo` at `.top`, `.bottom` and `.center` equal the wrapped form's under a lopsided padding; a wheel in the padding scrolls nothing. `ScrollViewReader.padding` and `.frame` stay the generic wrapper (the reader has no node): write the modifier on the scroller inside the reader.

**Gap 2 (`SP-N`, `SP-O`, divergence 250).** Probe `docs/probes/swiftui-scrollview-inset.swift` (run, output in its header): SwiftUI's `ScrollView` is an `AXScrollArea` (`HostingScrollView`), `.accessibilityIdentifier("transcript")` on it is that node's identifier, the children keep theirs and a child without one gets none. MetalUI had no node for a scroller; the generic wrapper pushed the identifier onto every leaf (the `VStack` rule, `DA-A`). `ProposalScrollView.accessibilityIdentifier(_:)` is now a concrete member: at prepaint the scroller registers its own node at the viewport bounds with the identifier and `.contain` (which `distributes` never hands down), so no wrapper and **no element request: 38 named against 38 bare, the `.contain` workaround 39**. A scroller with no identifier registers nothing (the tree has no group). The node is an `AXGroup`, not an `AXScrollArea` (`AccessibilityRole` has no such case; adding it means the AppKit and AccessKit role maps and their SDL parity tests, which this sandbox cannot run): divergence 250.

**Gap 3 (`CMG-G`).** The report's premise, that a positive `.scrollIndicators` margin moves the thumb inward, was untrue: `ScrollChrome` read only the margins along the scroll axis, so a trailing margin moved nothing. Probe `N0`..`N9`: SwiftUI accepts a negative margin (no clamp) and moves a vertical scroller by its trailing margin, a horizontal one by its bottom margin, inward when positive and outward when negative; the leading margin of a vertical scroller does nothing; along the axis a negative margin lengthens the track. `ScrollChrome.indicatorAcross` now reads the side the thumb sits on (`EdgeInsets.across(_:)`, also for the horizontal slot of a two-axis scroller) and `indicatorBounds` subtracts it. **Default geometry unchanged**: 3 wide at `maxX - 5`; the probe's knob slot is AppKit's own track and does not measure MetalUI's thumb. Alloy's flush thumb is `contentMargins(.trailing, -2, for: .scrollIndicators)` (`maxX - 3 ... maxX`); its row padding can also move instead. Right-to-left is unmeasured (the thumb stays right and reads `trailing`).

**The flex `ScrollView` (follow-up on the same PR).** Alloy's `ChatView` is `ScrollViewReader { ScrollView { LazyVStack ... } }`, the flex `ScrollView<Content: ElementGroup>`, which has no `ProposalElementGroup` padding at all. It gets the same members: `loweredLayout` wraps the viewport in a native padding node, records that node as the scroller's `LoweredItem`, and prepaint and paint read the viewport's bounds from `Layout.viewportNode`; the identifier registers the same `.contain` node. `defaultScrollAnchor` and `scrollPosition(id:)` chain after `.padding` in either order. `ScrollChrome` is shared, so the indicator margin reaches it. **Alloy's shape measured** (bottom anchor, `LazyVStack(spacing: 10)`, delta into the last row): bare 29, direct 29, Alloy's wrapped form 32 requests per delta, steady and streamed alike: 3 fewer, as reported.

**Tests.** `ScrollViewInsetTests` (new, 13: the 8 below for `ProposalScrollView`, plus the flex `ScrollView`'s parity with the wrapped form and the other modifier order, `scrollPosition` after a padding, the identifier node at bare cost, the thumb, and Alloy's shape 29/29/32): layout parity with the wrapped form, the inset scroll region, paddings that add, the count pins (38, 38, 40), the identifier's node and the rows' own ids, its zero cost (38, 38, 39), no node without an identifier, and the thumb's place under each margin. Flex `ScrollView` mutations, each caught: the padding node dropped, the viewport bounds not re-read, the identifier node not registered, `indicatorAcross` ignored (`scrollPosition` after a padding and the cost pins have no behavioural mutation: with the members removed `.padding` does not compile on the flex scroller and the generic wrapper cannot be forced). `ProposalScrollView` mutations, each caught: padding node dropped (parity, region and identifier-frame tests), viewport bounds not re-read in prepaint (same), second padding replacing the first (`paddingsOnTheScrollerAdd`), the padding members disfavoured so the generic wrapper wins (the cost pin, 3 issues), the identifier through the generic wrapper (cost, node), a node registered without an identifier, `indicatorAcross` ignored, trailing read as leading (the thumb test). No pin or ceiling moved.
