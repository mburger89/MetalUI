# 319 - `onKeyPress` on a proposal chain joins the chain (`KF-AD`)

Branch `fix/onkeypress-group-cost` from master `aad96831`. Class `A`, no divergence. Reported by Alloy against PR #318 (`KF-AC`, record 316): `.onKeyPress` appended to `VStack { … }.frame(…).onChange(of: …) { … }` added one element request to every steady frame per chain.

**Root cause.** Not a retention bug. `Frame.elementRequests` counts each `Element` entered as a group member (`GlobalElementID.enteringGroupMember`); a flat modifier chain (`ModifiedContent`) is one entry however many layers it holds, so `.frame`/`.padding` cost nothing extra. `onKeyPress` on a proposal group returned `KeyboardModifier<Self>` (`KF-H`), an `Element` of its own: one more entry, one more `StateBinder.bind`, on every frame. With no `.equatable()` nothing is retained at all, and inside a retained subtree a wrapper is skipped with the rest. A `.frame` written after the same `LifecycleScope` costs the same +1 (measured), so the wrapper is not special; the key-press wrapper was avoidable because its handlers need no node. (Alloy's report named `ElementGroupKeyPress.keyPressLayer()`; on the legacy path that is not reached: a `StyledElement` chain, and a scope over one by `ES-A`, take `StyledElement.onKeyPress` on its own layer at no cost, measured +0. The shape reported, a proposal `VStack` with `.frame`, resolves to `KeyboardModifier`.)

**Fix.** `LayoutModifier.keyboard(KeyboardLayer)`: a chain layer with no layout node and no paint, one identity level, registering the handlers at its bounds (`KeyboardModifier.prepaint`'s call, inside `sharingRegistrationsWithEffects`). `_KeyPressFolding` (a proposal `ModifiedContent` chain; `LifecycleScope` over one, forwarding inside) carries the five spellings, returning `Self`: the handler joins the outermost layer if it is a keyboard layer, else adds one (`KeyPressFold.swift`). A `KeyboardModifier` written over a folded chain takes the layer's handlers (it is the focus target; a layer inside it would not hear). The `ProposalElementGroup` and `ElementGroup` spellings gained `@_disfavoredOverload`: without it `x.onKeyPress(a) { }.onKeyPress(b) { }` was ambiguous (the fold wins the first call, `KeyboardModifier`'s own member the second).

**Alternatives.** (a) fold into the receiver's own layer: done, via the new layer kind (a proposal layer has no handler slot, and `ModifierLayer`'s would need the legacy flex node). (b) make the wrapper retained: not the cause. Not done: the plain `ElementGroup` form (`ForEach`, `Pair`) is a layout node with no chain to join and still costs its request; `.accessibilityElement`/`.accessibilityIdentifier` on proposal groups are their own `Element`s and still wrap.

**Before / after** (`FrameWork.elementRequests`, a steady frame, `VStack { Box() }.frame(width: 50, height: 50).onChange(of: 1) { }`): without 2; with `.onKeyPress(.escape)` 3 before, 2 after. The same on a bare chain (3 before, 2 after), with three and five chained handlers (2 after).

**Tests** (`Tests/MetalUITests/ElementGroupKeyPressCostTests.swift`, 8): the literal Alloy shape, three handlers, five spellings on a bare chain, the receiver's type kept (compile-time, including the two-call expression), routing (folded handler before the focused descendant's, later-written first), not focusable, `.focusable()` after a fold owning the handlers, and a legacy chain under a scope costing nothing. **Mutations shown red**: the request-count tests red with the fold's overloads disfavored (with 3, without 2); `LifecycleScope`'s conformance made inert (type test, compile error); the layer's registration off (routing test); the `KeyboardModifier` absorption off (`.focusable()` test, two issues); the layer made focusable (routing and not-focusable tests). Joining versus adding a layer is not observable in routing (an outer layer is an ancestor, so the order is the same) and is not pinned.

**Docs.** Ruling `KF-AD` (`KF-AC` item 5 points to it), the rule in `docs/rules/input-focus.md`, inventory family `key-press-fold` (class M).
