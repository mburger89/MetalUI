# 444: the AppKit content view is a container; the backdrop's effect view lives in it (`WB-I`; class M, no divergence)

Branch `fix/backdrop-container-view`, base master `697ea647`. No public API, no divergence (243 live, next label 251). Ruling `WB-I` (amends `WB-E`); next `WB-J`.

**Bug (Alloy, macOS 27.2, run from Xcode).** `warning: adding an unknown subview: NSVisualEffectView 0x... Break on _didAddUnknownSubview: to debug.` `AppKitWindow.setWindowBackdrop(_:)` inserted its effect view into `contentView.superview`, AppKit's private `NSThemeFrame`, which `WB-E` chose so that the host view stayed the content view. Unsupported, and a later macOS could break it.

**Audit.** In Sources only `AppKitPlatform.swift` used `contentView` (the assignment at creation and the backdrop insertion); `AppKitTitleBarPlacement` reaches its views through `standardWindowButton(_:)`, not `contentView` (the frame view is `container.superview` of the title bar container, unchanged). Tests: `AppKitContainerBackgroundTests` (updated), `PlatformTests` (`contentView?.effectiveAppearance`, inherited, still true), `AppKitAppShellTests` (`contentView?.superview?.hitTest`, the frame view, unchanged); other `contentView =` assignments are on their own windows. No `as? MetalHostView` cast of a content view anywhere; `Backends/SDL` has no AppKit window.

**Change.** `HostContainerView` (internal, `AppKitPlatform.swift`): `isAccessibilityElement` false. Created once with the content rect, `hostView` added filling it with `[.width, .height]` autoresizing, assigned as `contentView`, then `initialFirstResponder` and `makeFirstResponder` set to the host view. A material inserts the effect view into `hostView.superview` `.below` the host. No reparenting at runtime. The window's accessibility children read the same before and after (`MetalHostView`, three theme widget cells, a reparenting cell proxy); on master AppKit's own effect view sits in the frame view while the window is opaque and leaves when it is not, which the frame-view test accounts for.

**Tests (`AppKitContainerBackgroundTests`).** Reverted to master's `AppKitPlatform.swift`: `aMaterialBackdropPutsABehindWindowEffectViewUnderTheContent` (1 issue), `aBackdropNeverChangesTheFrameViewsSubviews` (2), `theEffectViewSitsInTheContainerBelowTheHostAndNoneRemovesIt` (6) and `theContainerIsTransparentToAccessibility` (1) go red. `theHostViewStaysTheFirstResponderThroughBackdropChanges` passes on master (AppKit chose the host as before); it goes red (1 issue) with the two responder lines removed from the fix. The container answering `isAccessibilityElement` true reddens the accessibility test (3 issues). `aWindowWithNoBackdropCostsTheSameSteadyFrameAsBefore` is a guard: 1 element request and 144 allocations (least of eight) on master and with the change.
