# Frame timing and signposts - decisions (prefix `FP-`)

Rulings for Alloy gap G7 (an external benchmark harness, Alloy, wants to attribute keystroke-to-pixels and scroll-frame latency to the app versus MetalUI). Branch `feat/frame-signposts` from master `9116adff`; record 222. Class `M` (MetalUI-only): no divergence label added or retired (live 209, next label 226, unchanged). **Next unused id: `FP-L`.** Public API: `FrameTiming`, `FrameTimingSample`, `FrameInputKind`, `Window.frameTiming`, `WindowRenderer.setPresentationObserver(_:)`, `HeadlessWindowRenderer.reportsPresentation` and `deliverPresentations(at:)`. Guide: `docs/frame-timing.md`.

## FP-A: opt-in, MetalUI-only, one object

Instrumentation is a `FrameTiming` a caller assigns to `Window.frameTiming`; `nil` (the default) records nothing. `METALUI_SIGNPOSTS=1` gives every new window a timing that also emits signposts (read once per window, `FrameTiming.fromEnvironment()`). SwiftUI has no frame instrumentation, so class `M`; the census family is `frame-timing`. Edits outside the new file are small and named: `Window.swift` (the property, three call sites), `Frame.swift` (a `timing` property and three one-line stamps; the only `Frame.swift` change), `Platform.swift`, the Metal renderer and surface, the headless renderer.

## FP-B: the sample, the clock and the stamps

A `FrameTimingSample` is `frameIndex`, the input (`inputKind`, `inputTimestamp`, `inputReceived`, `inputCount`), `tickStart`, `tickTarget`, `buildStart`, `drawableAcquired`, `layoutEnd`, `prepaintEnd`, `paintEnd`, `commit` and `presented` (the tick and drawable stamps: `FP-I`), all `UInt64` nanoseconds on `FrameTiming.now()` = `DispatchTime.now().uptimeNanoseconds`. **Why this clock**: it is `mach_absolute_time` on Apple platforms, the clock of `NSEvent.timestamp`, `CACurrentMediaTime()` and `MTLDrawable.presentedTime`, so the platform's own event and presentation times compare with our stamps without conversion; it is `CLOCK_MONOTONIC` elsewhere, never goes backwards and does not follow the wall clock. `ContinuousClock` was rejected (it counts sleep and has no relation to the event clocks); `Date` rejected (wall clock). `buildStart` is the first line of the frame function after the "is there work" guard, **before the drawable is acquired**, so a stalled `nextDrawable()` shows as the gap before `layoutEnd` (a frame that acquires none is abandoned and its input stays pending). `layoutEnd`, `prepaintEnd` and `paintEnd` are stamped in `Frame.renderOutsideDispatch`; a frame that builds more than once (lifecycle, toolbar, colour scheme, an abandoned retained replay) keeps the **last** build's stamps, which are after the first `buildStart`. `commit` is read the instant `finishFrame` returns `true`, before `framesDrawn` advances. Every stamp starts at `buildStart`, so a stamp never taken reads as zero-length and the tests assert strict increase.

## FP-C: zero cost off, zero allocation on

Off: one optional load and branch per input event (`Window.onInput`) and per frame (three sites), no clock read, no allocation. On: `FrameTiming.init` allocates the ring once (`ContiguousArray`, default 512); a frame overwrites its slot in place; the only per-event and per-frame work is `DispatchTime.now()` reads and struct stores. Pinned by `recordingAndNotRecordingAllocateTheSame` (the minimum allocation count of a steady frame is equal off and on), whose mutations are in record 222. `samples` allocates the array it returns, by design; read it off the hot path.

## FP-D: nothing is written from a phase

Input is noted by the platform's event handler (`noteInput`), settled when the handler returns (`settleInput(dirtied:)`); the phase stamps are four clock reads into a struct that is not tracked state; `onFrame` runs at the end of `drawFrameIfNeeded`, after `framesDrawn` advanced and after the atlas bookkeeping, outside every phase, so an `@Observable` or `@State` write in it dirties the window like input and the next tick draws it (`onFrameRunsAfterTheFrameAndItsWriteIsNotStale`). `onPresented` runs from the platform's presentation callback hopped to the main actor, never inside a frame.

## FP-E: signposts

`#if canImport(os)`, `OSSignposter(subsystem: "com.metalui", category: "Frame")`, only when the timing was created with `emitsSignposts: true` (or `METALUI_SIGNPOSTS=1`). Intervals **`Input→Frame`** (begins when an input event that dirtied the window is settled, ends at commit; the begin therefore trails the event by the handler's own time, which is the app's share) and **`Frame`** (frame start to commit, message the frame index); events **`Layout`**, **`Prepaint`**, **`Paint`** (each marks the phase's end, inside `Frame`) and **`Present`** (when the platform reports presentation). Linux and Windows have no `os`: the same ring and callbacks are the portable hook, `emitsSignposts` is `false`.

## FP-F: presentation

`WindowRenderer.setPresentationObserver(_:)` is a **defaulted** requirement (no defaultless requirement, no migration for a conformer): the default reports nothing, `presented` stays `nil`. Contract: the observer is called on the main actor, never inside `finishFrame`, once per finished frame, with a 0-based token counting `finishFrame` successes since the observer was installed; `Window` maps token to frame index with the timing's `framesRecorded` at installation. **Metal**: `MetalLayerSurface` adds `drawable.addPresentedHandler` before `present`, `presentedTime` (seconds, `CACurrentMediaTime`) times 1e9, `nil` when 0 (dropped); the handler hops to the main actor. `RenderSurface` gains a defaulted `present(_:in:onPresented:)`. **SDL**: SDL_GPU exposes no presentation callback, so `presented` is `nil` and documented; `commit` is the best available. **Headless**: `nil` by default (no display); `HeadlessWindowRenderer.reportsPresentation = true` plus `deliverPresentations(at:)` lets a test play the display.

## FP-G: input attribution

The kind is `.key` (key up/down, modifiers), `.text`, `.pointer` (mouse, drag, pinch, rotate, drop), `.wheel`, `.other`. **Only an event that left the window dirty counts** (a hover over nothing, an unchanged modifier report do not become a later timer frame's "input"); the earliest such event since the previous frame wins and the rest are counted in `inputCount`. `inputTimestamp` is the platform's own event time when it is on our clock (positive, before now, within the previous second: true of `NSEvent.timestamp`), else `inputReceived`. SDL timestamps and the harness's simulated ones are off-clock and fall back; the raw receive time is always `inputReceived`.

## FP-H: limits and carried

`inputTimestamp` on AppKit is the event's creation, `inputReceived` when the main run loop handed it over; the difference is queue latency, an `Input→Frame` interval begins later than either. `commit` is submission, not display; `presented` on Metal arrives one or two frames later and is filled in place (a ring that wrapped meanwhile drops it). Frames drawn while the renderer cannot supply a drawable record nothing. A window's `FrameTiming` is not shared across windows (`framesRecorded` and the token base are per window). Carried: SDL presentation time (needs a platform fence or the swapchain's present-timing extension), a per-phase `Frame`-level breakdown inside paint, a CI-run signpost trace.

## FP-I: the latency trace and the tick and drawable stamps (G34, record 268)

Two new stamps and two derived values on `FrameTimingSample`: `tickStart` (`FrameTiming.now()` read at the top of the display-link callback that drove the frame, `nil` for a frame drawn by a direct `drawFrameIfNeeded()`), `tickTarget` (that tick's `targetTimestamp`, `nil` when the platform reports none or it is off our clock), `drawableAcquired` (read right after `renderer.beginFrame()` returned, so `drawableWait` = `drawableAcquired - buildStart` is the time `nextDrawable()` blocked), and the derived `inputToTick` (`tickStart - inputReceived`) and `drawableWait`. `FrameTiming.noteTick(target:)` is called by `Window`'s tick closure and consumed by the next `beginFrame()`; a "Drawable" signpost event marks the acquire. The refresh interval is the shortest gap between consecutive on-clock tick targets (2 to 50 ms), `FrameTiming.refreshInterval`.

**`METALUI_LATENCY_TRACE`**, read with `METALUI_SIGNPOSTS` by `FrameTiming.fromEnvironment()`: unset, empty or `0` is off; `1` writes to standard error; any other value is a file path that lines are appended to (created if absent; an unwritable path falls back to standard error). Nothing is written unless a frame was caused by input and its presentation has been reported (Metal only), so a frame no input caused, and any frame on a renderer that reports no presentation, gets no line. A header line is written once, then one line per such frame, when `presentedTime` arrives:

```
metalui-latency idx kind n | ms: ev>recv recv>tick tick>build drawable build encode commit>screen | total frames
```

Columns (milliseconds, `-` for an unstamped stage): `ev>recv` event timestamp to the window receiving it; `recv>tick` the wait for the display-link tick; `tick>build` tick callback to frame start (gesture and tooltip advance); `drawable` `nextDrawable()` wait; `build` drawable acquired to end of paint (layout, prepaint, paint, and any extra builds); `encode` end of paint to commit; `commit>screen` commit to `presentedTime`; `total` event timestamp to presented; `frames` total divided by the refresh interval, `-` before an interval is known. `idx` is the frame index, `kind` the `FrameInputKind`, `n` the input count. Zero cost off (`FP-C`) is unchanged: the new stamps are two clock reads per frame and `noteTick` is one optional check per tick. Pinned by `aKeyThenATickStampsTheTickAndTheDrawableInOrder` and `theLatencyTraceWritesAHeaderThenOneLinePerPresentedInputFrame`. Class `M`, no divergence.

## FP-J: the trace applies to any `FrameTiming`, and its sink is flushed (record 269)

Found with Alloy (release build, real window, about 200 keys): the trace file was created and stayed 0 bytes. Root cause, `FrameTiming.fromEnvironment()` was the only place `METALUI_LATENCY_TRACE` was read, and it runs only for the default value of `Window.frameTiming`; an app that assigns its own recorder (`window.frameTiming = FrameTiming(capacity: 8192)`) discarded the env-built instance, which had already created the file but never saw a frame, while the recorder it kept had no sink. Rulings: (1) `FrameTiming.init(capacity:emitsSignposts:)` reads `METALUI_LATENCY_TRACE` itself, so every timing traces when the variable is set, however the window got it; `fromEnvironment()` now only decides whether to build a default one. (2) **Public `FrameTiming.enableTrace(destination:)`** (`"1"` standard error, else a path, unwritable falls back to standard error) turns it on from code. Class `M`. (3) The header is written on enable, not at the first presented frame (which never came when no sink was attached to the recording instance), once per destination per process. (4) The file is opened once per path (Foundation `FileHandle(forWritingAtPath:)`, positioned at the end; POSIX `open` with Unix mode bits aborts in the Windows CRT) and the handle shared by every timing (two windows no longer hold separate offsets and overwrite each other); each line is one unbuffered write, so it is readable while the app runs and survives a kill (the old `FileHandle.write` was also unbuffered, so buffering was not the cause). Ruled out by reading: a text-input event (`insertText` -> `.textInput`) is classified `.text` and counts when it dirties the window (`aTextInputFrameWritesATraceLineToTheFile`); `noteTick` is on the display-link path and only affects the tick columns, never whether a line is written; the presented handler reaches `notePresented` and the sink call there is the same for every platform.

## FP-K: re-entrant dispatch and the trace summary (record 273)

Alloy (release, on screen, ~600 keys posted with `CGEvent.postToPid` into a focused code view) still got the header and no data line after `FP-J`. **Read, not reproduced:** a text-input event reaches `dispatchTextInput`, which claims it and calls `setNeedsRedraw()` before the handler returns, and `insertText` is called by the input context outside `onInput`, so on the AppKit path the text case dirties synchronously and does not nest; the harness and AppKit agree. The re-entrant case is real in the code (an inner clean event nulled the outer candidate) though not on the Alloy path, so it is fixed, and counters say what happened in a run. **A late-claim heuristic (a clean input claimed by a frame within a bound) was written and removed:** it could attribute an unrelated timer frame to an input, and the measurement must stay exact. A clean input is still dropped. Rulings: (1) **Re-entrant dispatch keeps the outer event.** `noteInput` counts depth and a nested call does not replace the candidate; only the outermost `settleInput` settles. (2) **Counters, always kept** (integers, no allocation; nothing runs when `Window.frameTiming` is `nil`): `traceLinesWritten`, `presentedNoInputCount` (presented while tracing, no input kind), `droppedCount` (platform reported `nil` presentation), `settledCleanCount` (inputs whose handler left the window clean), all `package`. (3) **Summary line**, public `FrameTiming.writeTraceSummary()` on demand and automatically every 100 presentation reports, only when a trace sink exists: `metalui-latency-summary written=N presentedNoInput=N dropped=N settledClean=N`; fields never reorder, new ones append. Reading it: `written=0` with `presentedNoInput` large means presentations arrive for frames with no input; `dropped` large means the display reports nothing; no summary line means no presentation report reached the timing. Class `M`, no divergence. Pinned by `aReentrantDispatchDoesNotClobberTheOuterInput`, `aTrulyNoOpInputWritesNoLineAndIsCounted` and `theTraceSummaryCountsAndIsWrittenOnDemandAndEveryHundredReports`.
