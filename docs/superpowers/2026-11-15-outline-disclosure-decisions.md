## OG-A: the API (provisional; the `DisclosureGroup` part FINAL, record 311)

Class `A`, SwiftUI's spellings and generics exactly as design section 1: `DisclosureGroup` (the `Label: Element, Content` forms, `Label == Text` with `LocalizedStringKey` and `StringProtocol`, with and without `isExpanded:`; content `@escaping`, evaluated only when expanded), `OutlineGroup` (five generics, four inits), the content `List(selection:content:)` and the outline `List` inits, `contextMenu(forSelectionType:menu:primaryAction:)`. Not offered (class `R`): `DisclosureGroupStyle`, Table outlines, `.listStyle`, `Section` in a `List`. **As landed (lane 1):** `DisclosureGroup<Label: ElementGroup, Content: ElementGroup>`, an `ElementGroup` (`Sources/MetalUI/DisclosureGroup.swift`) over an internal `Component` body, with `init(content:label:)`, `init(isExpanded:content:label:)` and the `Label == Text` forms `init(_:content:)`, `init(_:isExpanded:content:)` over `LocalizedStringKey` and over `StringProtocol` (`@_disfavoredOverload`). **The generics are `ElementGroup`, one step wider than the design's `Label: Element`** (the repo's controls take `ElementGroup` labels, as `Toggle` does; every `Element` is one, so SwiftUI source compiles unchanged). `content` is `@escaping` and called only while expanded (`aCollapsedGroupNeverCallsItsContent`: 0 calls over three collapsed frames, 1 per expanded frame). `LocalizedStringResource` forms are class `R`. Probe backing: `swiftui-disclosure-group.swift` D2 (the `String`, `LocalizedStringKey` and literal title forms measure identically: 260 x 24 collapsed, label ink at x 32.5 in a 20-padded window; a `Label` label differs only by its icon, 34), D4 (an uncontrolled group is collapsed initially; `.constant(true)` is expanded at once).

**As landed (lane 3, `Sources/MetalUI/OutlineGroup.swift`):** `OutlineGroup<Data: RandomAccessCollection, ID: Hashable, Parent, Leaf, Subgroup>` with SwiftUI's five generics, an `ElementGroup` where `Parent: ElementGroup, Parent == Leaf, Subgroup == DisclosureGroup<Parent, OutlineSubgroupChildren>` (SwiftUI's `View` there); four inits, root element and collection, each `Identifiable` and with `id:`, `children: KeyPath<DataElement, Data?>`, `@ElementBuilder content: @escaping (DataElement) -> Leaf` (SwiftUI's `@ContentBuilder`). `OutlineSubgroupChildren` is a public empty `Component` (class `M`; SwiftUI's is opaque). **Not offered (class `R`):** the `Binding` forms (`OutlineGroup(_ data: Binding<C>, children: WritableKeyPath, content: (Binding<E>) -> Leaf)`). A `children` read of `nil` is a leaf, non-nil, **even an empty array**, is a group (a disclosure triangle with nothing below it; `theKeyPathAndIdentifiableForms...` pins it); SwiftUI's documentation says the same of `children`, and probe `P-L1` ran no empty array, so this is the documented reading, not a measured one.

**As landed (lane 4, `Sources/MetalUI/ListContent.swift`, `List.swift`):** MetalUI's `List` is one type, `List<Data, Row>`, so SwiftUI's `List<SelectionValue, Content>` is spelled as **constrained inits**: `List<ListContentRows<SelectionValue>, ListContentBody<Content>>`, the two placeholders being class `M` (empty, never constructed, `Data.Element: Identifiable` met by the empty `ListContentRow`). Inits: `init(selection: Binding<Set<SelectionValue>>?, content:)`, `init(selection: Binding<SelectionValue?>?, content:)`, the `@_disfavoredOverload init(selection: Binding<SelectionValue>, content:)` and `init(content:)` (`SelectionValue == Never`), content `@ProposalContentBuilder` with `Content: ProposalElementGroup` (a non-proposal member, an `OutlineGroup`, is adopted as `LegacyContent`, which flattens through). The outline inits are SwiftUI's eight, `List(_:[id:]children:[selection:]rowContent:)` over a Set, an optional, a disfavoured non-optional and no selection, each **literally `self.init(selection:) { OutlineGroup(data, [id: id,] children: children, content: rowContent) }`** (the row type `ListOutlineBody<D, ID, RowContent>` is a public alias). `rowContent` is `@ElementBuilder` returning an `ElementGroup` (`OutlineGroup`'s `content`). Not offered (class `R`): the `Binding<Data>` forms, `editActions:`, `.listStyle`, `Section` in a content `List` (a member that is not a unit source makes the list eager: it lays out and scrolls, its rows cannot be selected), `LocalizedStringResource`. A content list reads `Style` only for its decoration and handlers (`.onKey`, `.background`): its size is the lazy stack's (the proposal's width, the content's height).

## OG-B: flattening, identity and tree-wide ids (provisional; the lazy-stack flattening FINAL, record 312)

Design section 2 stands: one engine, nested named scopes per depth, selection and scroll ids are the element ids, so ids must be unique across the whole tree (Alloy: repo-relative paths). **Moving a node to another parent gives it a new identity**, as SwiftUI: probe `P-I1` (X moved from A to M with the same id: "disappear X" then "appear X" in one turn and the row's `@State` is NEW, born# 3 -> 6, while the unmoved sibling Y keeps 4 and the unrelated N keeps 5; the same in `List(_:children:)`, `List { OutlineGroup }` and the recursive `DisclosureGroup(isExpanded:)`). The divergence label that records tree-wide unique ids is reserved (1085-1094, see the decision-prefixes row). **As landed (lane 4, the list part):** the content `List` runs lane 2's lazy tree behind a `ListContentEngine` over `LazyStackEngine` (spacing 0, leading, each unit wrapped in a row of the list's own chrome), so the same `LazyUnitSource` flattening serves `LazyVStack` and `List`; the engine's ids are `LazyVStack`'s (the list's id is the stack's id) and the rows' own hit and accessibility ids are `list/named("row " + the table's key of the unit)` (a unit box's own key is NOT unique: an outline row's is its static source's). `List { OutlineGroup }` and the outline inits give the same element ids (`theOutlineInitsMakeTheSameElementIDsAsAListOfAnOutlineGroup`). The divergence label for the reveal is 1085; the other reserved labels (tree-wide unique ids, no `listStyle`, an unobserved out-of-window change, the one-level `⌥` cascade, the splice, AX rows, SDL nesting) stay reserved and unused.

**As landed (lane 2, record 312, `Sources/MetalUI/LazyTree.swift`):** a `LazyVStack` realises the ids the eager `VStack` numbers. Each level the flattening enters is entered as the eager path enters it: a `Component` through `enterComponent` (its id level, its `@State` bind, its one index), a `ForEach` element under the id-named scope of its slot (`FI-A`/`FI-B`), an `if` at its one slot (`ID-B`, `noteProduced` or `noteAbsent`), an `if`/`else` at both (the taken branch's slot produced, the other absent, an empty source holding the other index so every source consumes one cursor index), and a `DisclosureGroup` as its body `Component` whose bypassed `VStack` is level 0 and whose label row is member 0 and `if` slot member 1 of it. So a tree moved between a `VStack` and a `LazyVStack` keeps its `@State` (pinned by `theSameTreeKeepsItsStateMovedBetweenAVStackAndALazyVStack`: equal serials, and the lazy ids are the eager ids less the groups' own stacks). A unit's key is its element's key nested with its own level's key, unique tree-wide when ids are; an element's first unit is its scroll target (`scrollTo(element id)`). Duplicate ids inside one `ForEach` are not deduped by the tree source (the window's `LZ-G` dedupe still applies).

## OG-C: lazy flatten through a Component and an if/else (FINAL, record 312)

Extends `LZ-B`: a Component whose content flattens, and the taken branch of an if/else, stay lazy inside a tree. Not probed (a MetalUI-internal rule with no SwiftUI observable); lane 2 pins it.

**As landed.** The gate is the content's **type**, not a runtime probe: `lazyTreeCapableType` is true for `DisclosureGroup`, for `Pair`, `OptionalGroup`, `EitherGroup`, `LegacyContent` and `ForEach` over a capable member, and for a `Component` (not `Animatable`) whose `Content` is capable, and is cached per type. A `LazyVStack` whose content type is not capable reads exactly as before (`LZ-B`: a plain `if` is still eager and counted, divergence 636; a plain `Component` row is one unit; nothing moves for the 100k tests); `LazyHStack` shares the stack engine (so it flattens a capable tree too, untested); the grids still call `lazyFlatten` and are untouched. Inside a capable tree: a `Component` is materialised once and its content flattened under its own id; a `ForEach` becomes `LazyTreeForEachSource` (prefix sums per element, each element's content flattened under its scope; `locate` is `O(log elements)` and `O(log siblings)` per level below it); `if` and `if`/`else` contribute the taken branch's units; a `DisclosureGroup` contributes its label row and, while expanded, its content (`makeContent()` is never called while collapsed). A member that is none of these and is not a plain unit (a `for` loop's `ArrayGroup`, a `LegacyContent` of an unknown group) still makes the container eager.

**Cost, honestly.** The flattening evaluates the body of EVERY element of every expanded folder each frame (identity, `@State` bind, `if`, content closure of expanded groups), no layout; only the window is realised. Collapsed subtrees cost zero evaluations. This is design section 0's O(rows in expanded folders) light evaluation, until lane 8.

**Deliberate gaps (lane 7 and unmeasured).** The eager group's insertion fade (`XF-H`) is not recorded on the lazy path (no `noteOptional`/`noteEither`): a lazy outline snaps until lane 7's splice. The eager group lays its children in its own centre-aligned stack with 0 spacing; the lazy path bypasses that stack, so the children are placed by the LAZY container's alignment and spacing (equal to the eager layout for full-width children and spacing 0, Alloy's case; a narrow child under `alignment: .center` is no longer centred in the group's width, and a non-zero container spacing separates the label row from its children). SwiftUI's own behaviour of a `DisclosureGroup` inside a `LazyVStack` was not probed, so no divergence label is spent; lane 4's `List` forms fix alignment themselves.

## OG-D: the expansion model, retention, cascade and reveal (provisional; the `DisclosureGroup` storage FINAL, record 311)

- **Controlled `isExpanded:`** is read during the flatten and written only from input (chevron, keys, AX, ⌥ cascade). **As landed for a standalone group (lane 1):** the binding is read when the body is built and written by the label row's click, Space (while focused) and an accessibility press, each once, as the negation; never from layout or paint (`aControlledBindingIsWrittenOnlyByTheClickAndAProgrammaticWriteRerenders`: 0 writes over four frames, 1 per click, a programmatic write re-renders and is not written back).
- **Uncontrolled** `DisclosureGroup` is a state slot, collapsed initially (`D4`). **As landed:** the body `Component`'s `@State` (`$state0` under the group's own id; no new reserved slot name, so `theSevenRetentionSlotsAreMutuallyDistinct` is unmoved); it persists across frames and, as any `@State`, resets if the group's identity moves (`OG-B`). **Uncontrolled outlines retain descendant expansion**: probe `P-E5` (expand A, expand A/B, collapse A, re-expand A: A/B is still expanded, `A+ | A/B+ | A/B/D | A/B/E | A/C | Z | M-`) in `List(_:children:)`, `List { OutlineGroup }` and a content-form `DisclosureGroup` with no `isExpanded:`. One slot per subgroup, as design section 2; the slot survives the ancestor's collapse.
- **`OutlineGroup` storage, as landed (lane 3, record 313).** One `@State` slot per group, **the `DisclosureGroupBody`'s own `local`** (`$state3` under the group's component id, `DisclosureSlot`), so the outline and the hand-written recursive `DisclosureGroup` form agree on every id (`anOutlineGroupAndTheHandWrittenRecursiveFormHaveTheSameIdentity`; the structure is `OutlineGroupBody` Component, a `ForEach` of the roots, per element an `OutlineNode` Component holding an `if`/`else` of `DisclosureGroup` over a `ForEach` of the children or the leaf content; `OutlineScopes` names each level for the lazy path). **P-E5 retention is built in two places.** (1) The outline's disclosure never notes its content slot absent (`OptionalGroup.retainsStateWhenAbsent`, set through `DisclosureGroupBody.keepsHiddenState`), so a collapsed group's descendants are unevaluated, not reset: the eager form retains (a plain `DisclosureGroup` still resets, as lane 1 pinned). (2) The lazy index marks every expanded group's slot live each frame and keeps a `hidden` set of the expanded groups under a collapsed or unvisited ancestor marked too, because the state table reaps an unmarked slot past 256 entries after two frames (`TB-AH`); `aHiddenGroupsExpansionSurvivesTheStateTablesReaping` has 300 stateful rows in the table. **A removed node's expansion resets**: the eager form by the `ForEach`'s `noteLoop` (`DD-C`); the lazy form by `StateTable.noteRemovedSubtree`, which a rebuild calls for each group of the old index whose id is no longer a group while its parent is still expanded (a group under a collapsed ancestor keeps its state until it is visited). A group moved to another parent has another identity and starts collapsed (`P-I1`). A leaf's own `@State` keeps lane 2's bounded retention (`TB-AH`) and is not reset by the index.
- **⌥ cascade (`P-K4`, `P-K5`, `P-C1`).** In SwiftUI, ⌥→ on a collapsed group expands it and ALL descendants at once, and in the content form SwiftUI writes every descendant's `isExpanded` binding in the SAME run-loop turn, including the bindings of rows that had never been built (`K4d`: a 5-deep chain, four bindings written in one turn). ⌥← collapses the group and every descendant (two bindings in one turn); ⌥← on A/B leaves its parent open. ⌥-click on the chevron of a collapsed group expands it and its descendants at once (`C1c`). ⌥→ on an ALREADY expanded group does nothing (`K4b`: descendants stay collapsed). Alloy accepts MetalUI doing one level per frame with no cap (design section 3, 9a.4; divergence reserved): SwiftUI's same-turn cascade writes bindings of rows it has not built; MetalUI's lazy engine cannot know an unbuilt row's binding, so the cascade there is one level per frame and ends after the depth. That is a MetalUI engine constraint, not something the probe measured in SwiftUI.
- **Collapsing an ancestor of the selection (`P-K7`, Alloy 9a.5).** SwiftUI keeps the hidden id in the binding (no write: `selection` stays `A/B/D` after a chevron click or a programmatic collapse of A, and after collapsing A/B under a selection A/B/D) while the outline has NO selected row; the next arrow key starts from nothing (↓ selects the FIRST row, ↑ the LAST: `K7e`, `K7f`); a collapse by key on the selected group keeps it selected and ↓ moves to the next visible row (`K7d`). MetalUI follows this exactly: the controller keeps the id, shows no selection while it is hidden, and ↑↓ with no visible selection go to the first or last row.
- **Reveal (`P-R1`, Alloy request a).** In ONE transaction (insert the ancestors in the expanded set, set the selection, `proxy.scrollTo(id)` with the default, `.center` or `.top` anchor) SwiftUI does NOT land the row in view, in the same update or in the following second (row 20 stays at y 650 of a 400 high view, `scrollY` 0, 60 frames sampled); `scrollTo` on the next main-queue turn (0 ms) also fails; `scrollTo` 20, 60 and 120 ms later (one frame or more) lands it at y 368 of 400 (`scrollY` 282, the row's bottom edge on the view's bottom edge: the nearest alignment of the default anchor, since the row was below the viewport). The controls (`R1d` expand, wait 6 turns, scroll; `R1e` already expanded and off-screen, `scrollTo` at once: y 368, `scrollY` 4954) land at the same place. So the requester's "must land the row in view" is STRONGER than SwiftUI: MetalUI is asked to land it in the same transaction. Ruling: the lane that builds reveal makes a `scrollTo` of an id that the same transaction made visible resolve against the post-expansion flatten (the expansion is applied to the index first, then the scroll target is resolved), and the test asserts the row in view the same frame, not "as SwiftUI"; a divergence (a stronger guarantee than SwiftUI's) is reserved for it. The nearest alignment is the default landing (bottom edge for a row below the viewport); `.center` and `.top` were measured only in the failing arm, so their landing positions are unknown and follow the existing `scrollTo` anchors.
- **Same-transaction expand + `scrollTo` (Alloy, 2026-11-15, accepted).** Alloy accepted that MetalUI resolves a `scrollTo` made in the same transaction as the expansion against that frame's post-expansion layout, so the row lands in view in the same frame, **unlike SwiftUI**, which needs a frame in between (`P-R1`). The labelled divergence (a stronger guarantee than SwiftUI's) is added by the lane that implements it (lane 4 or 5) from the reserved 1085-1094; lane 1 adds none.
- **Reveal as landed (lane 4): `OG-L`, divergence 1085.**
- **Expanded-folder scroll (Alloy 9a.7).** Expanding does not scroll (`N1`: rows below slide, nothing scrolls); a newly expanded folder is not scrolled into view.

## OG-E: keys, selection and focus (FINAL: lane 4 the selection and focus, lane 5 the disclosure keys)

List is the single focusable; rows are not (`FC-F`). Selection extracts to a `ListSelectionController<ID>` shared by both forms (design section 3). Measured key behaviour, identical in the three forms (`P-K1`..`P-K7`), is the spec; unless a lane finds a reason, MetalUI matches it:

| Key | On | SwiftUI (macOS 27.2.1) |
|---|---|---|
| ↓ ↑ | any | one VISIBLE row per key, one binding write per key, one turn apart (K1) |
| → | collapsed group | expands, selection stays (K2a) |
| → | expanded group | nothing; does NOT move to the first child (K2b) |
| → | leaf | nothing (K2c) |
| ← | expanded group | collapses, selection stays (K3a) |
| ← | collapsed root | nothing (K3b) |
| ← | leaf child | selection to the parent (K3c) |
| ← | collapsed child group | selection to the parent (K3d) |
| ← | expanded child group | collapses it, selection stays (K3e) |
| ⌥→ | collapsed group | expands the group and every descendant (K4a, K4d) |
| ⌥→ | expanded group | nothing (K4b) |
| ⌥← | expanded group | collapses it and every descendant (K5, K5b) |

The design draft's "→ expanded: first child if SwiftUI does that" is settled: SwiftUI does not. **The chevron click does not select** (`P-C1`: nothing selected stays nil, selection Z stays Z, the toggle is the only write); a plain click on the row body selects and does not toggle; ⌥-click on the chevron cascades. The key moves reveal the lead (the AppKit lead is the selected row). Out of scope (Alloy 9a.6): type-select, drag and drop, rename, multi-select.

**As landed (lane 4, selection and focus):** `ListSelectionController<ID>` (`Sources/MetalUI/ListSelectionController.swift`) owns the click, key and accessibility selection over a `ListRowSpace` (the row count, the id at a position, the position of an id) and a `ListLeadStore` (where the lead and anchor live); the data `List` builds one over `data` and its `ListOrigin`, the content `List` over its lazy units and a lead entry of its own (`list/$listlead`: the lazy stack's `LazyOrigin` is at the list's id and the table keys by id alone), so the data list is behaviour-neutral (every existing selection, key and accessibility test is unchanged; the only edit to a test is the static count of `withState` sites, `everyStateWriteSiteIsClassified`). **A content row's selection value** is its element's `.tag(_:)` when that casts to `SelectionValue`, else the id the unit is known by (a `ForEach` element's id, an outline row's element id, the first unit of a `ForEach` element holding a `DisclosureGroup`: the folder's id) when that casts; a unit with neither is not selectable and the keys step over it. **The list is the single focusable** (`isFocusable` on the list's own handlers, the rows register a hit target and an accessibility row but no focus; the chevron is an `onTapGesture` on a plain cell, so it is not a tab stop); a click on a row focuses the list. **Keys landed: ↑ and ↓** over the visible units, one row and one binding write per key (`P-K1`), clamped at the ends, a Set selection collapses to the row (⇧ extends from the anchor, as the data list); **a hidden selection** (`P-K7`): the binding keeps the id and no write happens, no row reads selected (the reader finds no row), and the lead is nil so ↓ selects the first and ↑ the last visible row. **The key moves reveal the lead** by enqueuing `scrollTo(the unit's scroll id)` (nearest edge). **Click** (`P-C1`): the chevron cell (13 wide, the row's height, at x `12 + 12 * depth`) toggles and does not select; a click anywhere else on the row selects and does not toggle. **← → and ⌥ (`P-K2`..`P-K5`) and the accessibility nesting are lane 5**: until then → ← do nothing in a content list, and a row's accessibility element is a sibling of its content's text (the content's ids hang under the list, not under the row's id), published with the row's index and selected state and selectable by a client.

**As landed (lane 5, the disclosure keys, `Sources/MetalUI/ListContent.swift` `disclose`, `ControlKeys.outlineDisclosure`, `OutlineCascade.swift`):** a `ControlKeys` row (`outlineDisclosure`: ← and →, no modifier or ⌥ alone; ⇧, ⌘ and ⌃ decline) composed after `listMove` in the content list's own `onKey`, for a list whose content type holds a disclosure, acting on the LEAD row (the selected row; no lead, nothing happens; the key is consumed whenever the content is hierarchical). **→**: a collapsed group expands (the selection stays, one binding write); an expanded group and a leaf do nothing (`K2b`, `K2c`: not the first child). **←**: an expanded group collapses (selection stays); a leaf, a collapsed child group and (nothing) a collapsed root: the parent is the nearest row above at a lower level, selected through the controller (`ListSelectionController.select(position:)`, the shared commit of a move; a Set selection collapses to it) and revealed like any move; a collapsed root does nothing (`K3a`..`K3e`). **⌥→** on a collapsed group expands it and every descendant; on an expanded group nothing even with a collapsed child (`K4b`). **⌥←** on an expanded group collapses it and every expanded descendant; on a leaf or a collapsed group it acts as ←, so ⌥← on a child leaf selects the parent and leaves it open (`K5b` measured the expanded child: it collapses itself and the parent stays; a ⌥← on a leaf was not probed, MetalUI's choice). **⌥-click on the chevron** cascades the other way from the group's state (open: collapse all; closed: expand all, `P-C1`): the chevron is an `onClick` now, not an `onTapGesture`, because only a click reads the mouse-up's modifiers (`ClickDispatch.modifiers`; a tap gesture's closure reads none), and it is hidden from accessibility as a whole (lane 1 hid only its glyph; the click target's own record would have published a button). The two forms differ in HOW the cascade runs, not in what it does: see `OG-M`. Input does the same to a unit without realising it through `LazyUnitSource.lazyDepth` and `lazyDisclosure` (a group's `isExpanded`, `set` and `cascade` read live), which a nested source, a `ForEach` of trees and an outline's source forward by unit.

## OG-F: accessibility (FINAL for the outline, lane 5; the standalone group is MetalUI's choice, record 311)

Probe `P-A1`/`P-A2` (the AppKit elements, read in process through the legacy attribute API; identical in the three forms): outline role `AXOutline`; row role `AXRow`, subrole `AXOutlineRow`, role description "outline row"; `AXDisclosureLevel` = depth (0, 1, 2; read-only); `AXDisclosing` 1 or 0 on a group and settable (setting it true on a collapsed row expanded it and wrote the binding: so the "expand" AX action is the `AXDisclosing` write), 0 and read-only on a leaf; `AXDisclosedByRow` = the parent row (nil for a root); `AXDisclosedRows` = the direct children rows (a leaf: none); `AXSelected` settable. **`AXExpanded` is not an attribute of an outline row at all.** The row's only child is an `AXCell` whose only child is an `AXDisclosureTriangle` (`AXValue` 1 expanded, 0 collapsed, action `AXPress`, which collapsed A and wrote `isExpanded[A] = false`). So the neutral model's "expanded" maps to `AXDisclosing` on macOS rows, and the disclosure triangle is a child (design section 4's "triangle child if probe P-A shows one" is settled: yes). **Lane 1 as landed (a standalone group, MetalUI's choice: `P-A3` is unmeasured, so nothing here is SwiftUI's):** the label row publishes as `AccessibilityRole.disclosureTriangle` (AppKit `AXDisclosureTriangle`; SDL/AccessKit `BUTTON`, the `accesskit.h` header is not fetched on the lane's machine so no new C name was used, and the AccessKit `expanded` state is left to lane 5), through a role hint (`AXNode.roleHint == .disclosureTriangle`, stripped like the other role hints), with the label's text as its label (the chevron is `accessibilityHidden`: unhidden, its symbol label "Forward" folded in), value `"1"` expanded and `"0"` collapsed (the value the outline probe read on the real triangle), focusable, press toggling it and refused when disabled. **Not measured:** SwiftUI's own AX elements (the label inside a cell; a standalone `DisclosureGroup`, `P-A3`): the in-process tree is one empty `AXUnknown` group, and an `AXUIElement` client of this process answered only with application-role elements in this environment. The standalone group's role, value, label and press are therefore taken from the outline's: a group row with a disclosure triangle child; a lane (1 or 5) re-measures with a live AX client before it ships the standalone group's AX. SDL/AccessKit: `TREE`/`TREE_ITEM` with expanded, level and EXPAND/COLLAPSE (design section 4; names verified in lane 5).

## OG-M: the ⌥ cascade over a content list's bindings (FINAL, lane 5, divergence 1086)

SwiftUI writes every descendant's `isExpanded` in the key's turn, rows never built included (`P-K4d`: a five-deep chain wrote four bindings in one turn). **MetalUI cannot write them from the input handler:** a group's content is a closure the app wrote, evaluating it takes a layout pass (a component's `@State`, its environment), and a binding is written from input, never from layout (`RW-I`); evaluating the closure off-window at input time would run a `Component`'s body with no state bound and no environment. So the key (and the ⌥-click) writes only a REQUEST, an entry of the list's own state (`list/$listcascade`: group id to the wanted state), and the build it dirties carries it out (`OutlineCascade`): an **expand** builds the group, and every group below it, as expanded for that build (so the whole subtree is flattened at once and every descendant's content is evaluated and its own bindings reached), and each group that was not expanded queues its own write; a **collapse** builds as it is and each expanded group queues its write of `false`. The queued writes run after the build, in ONE drain (`LifecycleStore.enqueue`, the seam `CodeView` uses, `LC-E`), and the window then builds again inside the same `beginFrame` and presents that build, so **the first presented frame already shows the final state**; the drain's last event spends the request. **Measured:** the five-deep chain's four bindings are written in one drain with no build between them (`optionRightOverAFiveDeepChainWritesFourBindingsInOneTurn`: the layout count does not move between the writes), the same for ⌥← and ⌥-click, and the frame the key presents holds the whole chain. **What differs from SwiftUI (divergence 1086):** the writes run in the drain after the build that follows the key, not in the key's own handler, and a collapse reaches only the groups a flatten walks (every expanded group under an expanded ancestor), not an expanded group under an already collapsed child (SwiftUI's own reach there was not probed). **The data form** (`List(_:children:)`, `OutlineGroup`) needs none of this: its expansion is a state slot named by the row's ids, so the key walks the data below the group (iteratively, `OutlineGroupSource.cascade`) and writes every slot in the key's turn; an expand writes every group, a collapse every expanded one, and the index rebuilds once (`expansionGeneration`).

## OG-N: `contextMenu(forSelectionType:menu:primaryAction:)` and the click count as landed (FINAL, lane 6, record 317)

## OG-O: the content form's flatten cache (FINAL, lane 8, record 318, divergence 1087)

It then applies the journal and hands back the cached sources; only the window is realised. **A miss** walks as in lane 2 (counted `outlineContentRebuilds`, and `outlineContentEvaluations` per `ForEach` closure, component body and group content) and records.

**What the cache refuses** (the walk runs every frame, as before, correct and as slow; `OutlineWalk.unobserved`): a component holding a class instance that is not `Observable` (checked once per component type from its first instance) or declaring `@Environment`, a `ForEach` over such instances; a top level that cannot be compared (a closure field such as a `Binding(get:set:)` a row holds, a `DisclosureGroup` written directly in the list); a walk that wrote state, made layout nodes or lowering records, moved an audited channel (animations, lifecycle, presentations, scroll keys) or noted a lifecycle, presentation or window-preference record; a pending ⌥ cascade (`OutlineCascade.context.pending`), which also drops the cache. Every lane 2 to 6 test that models a tree with a plain class stays on this path and unchanged.

**Divergence 1087** is what remains: a value observation cannot see and the top level does not hold, that is a plain (not `Observable`) class reached only through a closure a row captures (a `DisclosureGroup` content closure, a `Binding(get:set:)` over plain data) or below an `@Observable` object's property, changes with no frame to show it until something else invalidates the cache (an observed or bound-state change, the top level's value, the ambient) - where before lane 8 the next drawn frame re-walked and showed it. SwiftUI shows such a change when anything re-evaluates the body. The escape is to make the model `@Observable` (Alloy's is). **The session's granularity is the list's:** any observed change re-walks the whole tree once (every expanded folder's rows), not the rows that changed; a per-element session would arm one observation per row. **A flat list of 100 000 roots** pays the top-level comparison (100 000 closure calls and compares) on every frame; Alloy's tree has few roots. Test switch: `ContentMemoStore.cachesOutlineContent` (`package`).
