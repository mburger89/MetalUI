# Block markdown - decisions (prefix `BM-`)

Rulings for Alloy gap G2, block markdown for chat replies. Plan: four PRs, the pure parser first. Branch `feat/markdown-parser` from master `b0fa5ae5`; record 231 (230 is the symbol-images line). Class `M` (MetalUI-only; SwiftUI has no block Markdown): no divergence added or retired (labels untouched). **Next unused id: `BM-K`.** `BM-A`..`BM-D` are PRs 1 and 2, the parser and streaming append (record 231); `BM-E`..`BM-J` are PRs 3 and 4, the views, theme, code fences, tables and demo (record 235, branch `feat/markdown-views` from master `1fa45020`).

## BM-A: a pure portable target that imports nothing

`MetalUIMarkdown` is in the portable manifest list (`PC-A`), imports **nothing** (no Foundation, no `MetalUICore`, not even `Observation`), has its own library product so an app (Alloy) can parse without any UI, and `MetalUI/App.swift` re-exports it (`@_exported import MetalUIMarkdown`). It does block structure only: inline content stays a `String` of raw Markdown that a view parses with the inline parser `Text` already uses (`parseInlineMarkdown`, `RT-B`), so inline semantics are identical to `Text`'s and `RT-B` code does not move. The input is UTF-8 bytes; the parser is a port of cmark-gfm's line-by-line container matching (`blocks.c`: open containers, then new block starts, then the line's text) onto an index-linked arena, so a parse allocates one array of nodes, not an object per block. Foundation's `AttributedString(markdown:)` with `.full` is Darwin-only and so cannot be the parser (`PC-A`); on Darwin it is the oracle instead (`BM-B`).

The public surface is `MarkdownDocument` (`init()`, `init(parsing:)`, `append(_:)`, `blocks`, `version`), `MarkdownBlock` (`id`, `kind`), `MarkdownBlock.Kind` and `MarkdownTableAlignment`; `MarkdownParseStats` (`bytesScanned`, `bytesCompared`, `blocksFinalized`, `bytesCopied`) is `package`, raw-pointer memory like `RopeStats`, for the counted-work pins.

## BM-B: v1 scope, and what Foundation says (the oracle)

v1 covers CommonMark 0.31 block structure as cmark-gfm parses it: ATX and setext headings, paragraphs, fenced code (the info string's first word is the language) and indented code, block quotes, bullet and ordered lists (nesting, start numbers, tight versus loose, the content-column rule, `1.`/`1)` as one type of ordered list, a new bullet character starting a new list), thematic breaks, GFM tables, and tabs as 4-column stops. **Carried, not in v1, and read as paragraph text (which is also what Foundation does with a task box):** link reference definitions and reference links, HTML blocks, task-list checkboxes, footnotes, math.

Readings that set the rules (probe `docs/probes/foundation-markdown-blocks.swift`, arms B1-B30):

1. **Soft and hard breaks (B1-B3).** A soft break is a `" "` run, a hard break (two trailing spaces or a backslash) a `"\n"` run. A paragraph's lines are therefore kept joined with `"\n"` and the inline parser decides; the view's default for a soft break is a space (`BM-E`, PR 3).
2. **Tight versus loose is invisible to Foundation (B7, B8).** The two carry identical intents, so the oracle cannot test it: `.list(tight:)` follows cmark's rule (a blank line between two items, or between two blocks of an item that are not both last) and is pinned by `BlockKindTests.listsAreTightOrLooseAndKeepTheirStartNumber`, not by the oracle. (The plan's oracle mutation "drop the loose rule" is therefore applied to that test.)
3. **The language is the first word of the info string (B9).** Foundation's hint is the whole string (`swift linenos`); the oracle compares first words. A backtick fence whose info string holds a backtick is not a fence.
4. **Tables.** A table is a header row (the paragraph's *last line*; earlier lines stay a paragraph, B17) plus a delimiter row with the same column count. Cells split at unescaped pipes (`\|` is a pipe), outer pipes are optional (B27), a bare `:-` can be the delimiter row (B28), rows are padded with empty cells or cut to the header's width (B5), and a row continues until a blank line or a block start. "No alignment" is `.none` in `MarkdownTableAlignment`; Foundation has none and reports left. **A delimiter-looking line that failed to match a paragraph's last line poisons that paragraph for good** (B18, B19: `a / |-|-| / |-|-|` is a paragraph); an indented or lazy delimiter-looking line makes no attempt and does not (B20, B21). Foundation's mechanism is not known; the parser's `tableRefused` flag reproduces every reading.
5. **Empty containers have no text and so no run (B14, B22, B23).** Empty items, quotes, headings, fences and cells are present in `MarkdownBlock` (an empty item is `[]`, so ordinals survive: the next item keeps its number) but the oracle drops them on both sides; a fence holding one blank line is the same as an empty one (`code` is `""`).
6. **A fenced block records whether it closed** (`isClosed`); Foundation does not report it. A fence that ran to the end of its container is not closed.

The oracle (`MarkdownBlockOracleTests`, Darwin) compares kind trees, heading levels, list ordinals, code text and language, table alignments and non-empty cells, and paragraph plain text through `parseInlineMarkdown`: **zero disagreements** over all 28,561 four-line sources of thirteen line kinds and 20,000 seeded longer ones. The normalisations of items 2, 3 and 5 are the only rulings against Foundation; none hides a difference in what is drawn.

## BM-C: finality, the tail, and the half-typed line

`MarkdownDocument` holds `finalBlocks` (append-only), the bytes from the start of the last top-level block (`tail`, in a class box so a copy shares it until one copy appends) and `tailBlocks`. An `append` adds the bytes to the tail, parses the tail with a fresh parser, moves every block but the last into `finalBlocks`, and drops the bytes before the last block's first line. **A block's start offset is the first line that opened it** (for a table split from a paragraph, the header line). Cost per token is O(tail), independent of earlier blocks; the divergence of a copy is *counted* (`bytesCopied`, a manual `isKnownUniquelyReferenced` copy of the tail only) so the pin can fail.

**The plan's finality rule ("every block that starts before the last is final") is false for a half-typed line, and test 4 found it.** Streaming a corpus one scalar at a time reached back in several shapes, all the same cause: what a line starts is decided from its first characters, and a later character on the same line can reverse it. `-` is a list item until it becomes `-|-`, a lazy continuation of the paragraph above; `#` is a heading until it becomes `#a`; `1` then `1.` can join the list above after a blank line; `|` is not a table row until `|-|-|`; and a delimiter row typed `|-` makes a one-column table out of the paragraph's last line before `|-|-|` unmakes it. Ruling: **while the input ends in a line with no newline whose bytes so far are only block-structure characters (spaces, tabs, `# > * + - _ = | : . ) ~`, digits, or a line opening with a backtick fence), the block before the last is parsed again too**; a line holding any other byte, or a newline, is final for every decision taken from its start. The extra block is bounded by that line's structure-only prefix, not by the length of a paragraph being typed (a letter ends it), and a counted pin shows both costs. Complete lines never reach back (the exhaustive corpus below agrees with whole parsing), and the supposed hazards of the plan (setext, lazy continuation, list continuation after blank lines) all act on the open last block.

Blank lines before the first block are dropped; when the tail is only blank lines, bytes from the start of its last line are kept (that line may be indentation).

## BM-D: ids

A top-level block's id is its ordinal in the document; a nested block's is its ordinal in its quote or item. Stable because blocks before the last are final and `finalBlocks` only grows. A block that changes kind (a paragraph becoming a setext heading or a table) keeps its id; the table split from a paragraph takes the next id (the paragraph keeps its own). Ids are never hashes: a hash would move with the text.

## BM-E: view lowering per block kind

`MarkdownView` (`init(_: MarkdownDocument)`, `init(_: String)`) is a `Component`, `Equatable`, and a `ProposalElementGroup`; `MarkdownBlockView` (public, `init(_: MarkdownBlock)`) is the same for one block, so an app can put blocks straight into a `LazyVStack` and a long reply windows block by block. **`MarkdownView.==` is O(1)**: the document's storage identity (`MarkdownDocument.identity`, `package`: the `ObjectIdentifier` of the tail box, valid because every holder keeps the box alive and a copy that appends takes a box of its own) and `version`, the theme, and the highlighter's `ObjectIdentifier`; a `String` source compares by `==`. Content is a leading `VStack(spacing: theme.blockSpacing)` over `ForEach(blocks, id: \.id)` of `MarkdownBlockView(...).equatable()`; **every nested component is `.equatable()` too** (a component inside a memoized getter's value is otherwise evaluated by the layout recursion each frame: measured, the highlighter was called three times for an unchanged fence). A block is a single-child leading `VStack` framed `maxWidth: .infinity` (a code box and a quote fill the width whatever they hold; the `VStack` also makes a `Divider` read a vertical stack).

| Kind | Lowered to |
| --- | --- |
| Paragraph, heading | one `ProposalText` over `collapsedTextContent` of `parseInlineMarkdown` runs through `markdownRunRequest`; an inline code run gets `theme.inlineCodeBackground`; a heading takes `theme.headingFonts[level - 1]` and `.accessibilityAddTraits(.isHeader)` (the level is not published: no API) |
| Soft and hard breaks | decided **before** parsing (the inline parser keeps a break as written): a soft break is a space (`MarkdownSoftBreak.space`) or a `"\n"` (`.lineBreak`); the spaces before a hard break are trimmed (`MarkdownInlineLowering.prepared`) |
| List | a `VStack` of `MarkdownListItem`s (`.equatable()`, so only the streaming item builds); an item is `HStack(.firstTextBaseline, spacing: listMarkerSpacing)` of a marker `frame(width: listMarkerWidth, alignment: .trailing)` and a `VStack` of its blocks; bullets `\u{2022}`, `\u{25E6}`, `\u{25AA}` by depth (accessibility hidden), ordered markers `start + i` followed by a dot; a list nested in an item is padded `listIndent` leading; tight lists space items by `listItemSpacing`, loose ones by `blockSpacing` |
| Block quote | the blocks in a `VStack`, padded `quoteBarWidth + quotePadding` leading, with the bar a **background attachment** (`.background(alignment: .leading)`), so it is proposed the quote's size and is exactly as tall as the content (a bar in an `HStack` would be 10 tall under a nil height); `quoteForeground` as an environment write |
| Thematic break | `Divider()` |
| Code block | `BM-H` |
| Table | a `Grid` (`BM-H` for its scroller): header cells bold, `gridColumnAlignment` from the delimiter row (`.none` is leading), a `tableRule` rectangle row before every body row; cells are `ProposalText`s of the inline parse |

The accessibility tree of a code block is `BM-I`. A `String` source keeps its last source and document in a `@State` class box (`MarkdownSourceMemo`): a longer source whose first bytes equal the old one appends the rest (the comparison is counted as `MarkdownParseStats.bytesCompared`), anything else parses afresh; it is an idempotent memo, so a retained double build is safe. Alloy should hold a `MarkdownDocument` and call `append` per token.

**Measured cost of a token (test 13).** A token appended to the last paragraph of the last of 10 or of 200 replies costs 2 content evaluations (the reply's `MarkdownView` and the one changed block) and nothing else is evaluated; the changed paragraph is shaped twice (its ideal and wrapped measures). **A reply whose unchanged blocks hold rich text re-measures them**: a rich `Text` has no layout-memo key (`IV-`) and taints its ancestors, so the layout of the *changed reply* measures its rich blocks again (2,200 bytes for the fixture reply, equal for both transcript sizes; with no inline markup in the reply only the changed paragraph is shaped). That is O(rich blocks of that reply), independent of the transcript, and it is the plan's stop condition about a keyed leaf for rich `Text`: **not widened here**, carried to a separate ruling with its own key and covering test (`BM-J`).

## BM-F: the highlighter contract

`protocol MarkdownCodeHighlighter: AnyObject { func highlight(code: String, language: String?, isClosed: Bool) -> [MarkdownCodeRun] }`, set with `.codeHighlighter(_:)` on either view; the default is plain text. It is **not** `@MainActor` (a plain `AnyObject` protocol, as promised to Alloy); it is called while a fence's component is built, **once per change of that fence** (the fence is `.equatable()` over its code, language, closed flag, theme and the highlighter's identity) and never on a frame where nothing changed, and it must be a pure read of its arguments. `isClosed` is false while the fence streams. `MarkdownCodeRun` is `Hashable, Sendable` with a UTF-8 `range` and a `CodeStyle` (colour and background, as `CodeView`'s). The view sorts runs by start, clips them to the code's bytes and against each other (an earlier run keeps the bytes it covers) and snaps an end that falls inside a scalar down to the scalar's start. The view holds the highlighter strongly and compares it by identity: change colours by giving another instance (a mutation that drops the identity from the fence's `==` leaves a new instance uncalled).

## BM-G: the theme is a value, not an environment key

`MarkdownTheme` is a plain `Equatable, Sendable` struct (fonts, colours, spacing, `codeWraps`, `tableScrolls`, `softBreak`), stored on the views and applied with `.markdownTheme(_:)`, which returns a copy. A subtree under a custom environment key cannot be replayed from a retained record (`SB-`), and a settled transcript must be; test 15 pins that unchanged blocks are hits with nothing ineligible.

## BM-H: code blocks, tables, and the horizontal scroller

A code block is `MarkdownCodeFence` (`.equatable()`): a rounded box (`codeBlockBackground`, `codeBlockCornerRadius`, `codeBlockPadding`) holding an optional language caption and a column of `MarkdownCodeChunk`s, **at most 32 lines each**, each an `.equatable()` monospaced `ProposalText` over the chunk's lines with the highlighter's runs sliced to it by UTF-8 bytes (`MarkdownCodeSlicing`): a streamed token changes the last chunk and shapes at most 32 lines whatever the fence's length (test 14: a 69-line and a 485-line fence shape the same bytes). **Measured, and the plan's stop condition: a horizontal `ScrollView` takes a vertical wheel for itself**: a wheel over a code block in a horizontal scroller scrolls nothing (long lines or not, test BM2), so the transcript around it stops while the pointer is over the block. Ruled: **`codeWraps` is true by default** (no scroller; lines wrap at the box's width) **and tables do not scroll by default (`tableScrolls` false; cells wrap)**; a theme that sets either off gets the horizontal scroller and the swallowed vertical wheel, **pinned wrong on purpose** (test BM2's `codeWraps = false` arm: a framework change that passes the wheel on reddens it and is a fix). `defaultScrollAnchor(.bottom)` is unharmed in both arms (the pin follows tokens after the wheel back to the end). Carried: a wheel that passes its other axis to the enclosing scroller.

## BM-I: accessibility

A heading is `.accessibilityAddTraits(.isHeader)` (role `.heading`, label the text; no level is published). A paragraph is static text with one `.link` child per link run, clicks through `\.openURL` (`LI-A`; test 9 reads `HeadlessPlatformWindow.openedURLs`). Bullet markers are hidden; ordered markers are read. **A code block is a `.contain` group labelled with its language (`"Code"` without one), its chunks readable inside it**: the plan said "combined under a label", and `.combine` with a label was measured to drop the code from the tree (one node whose label is the language and no value), so the group keeps its children instead. Table cells are static text in reading order; no table role is published in v1.

## BM-J: carried, not in v1

Link reference definitions and reference links, HTML blocks, task-list checkboxes, footnotes and math (`BM-B`); text selection across blocks (static `Text` has none on master; carried to whatever adds `textSelection`); a copy accessory on code blocks (the app wraps `MarkdownBlockView` for `.codeBlock` and copies `code`; a built-in accessory closure would make the view uncomparable); the heading level in the accessibility tree (no API); a keyed leaf for rich `Text`, so the unchanged rich blocks of a streaming reply stop being re-measured (`BM-E`; owes a key, a covering test and `METALUI_VERIFY_LAYOUT_MEMO=1`); a horizontal scroller that passes a vertical wheel on (`BM-H`); a table role in the accessibility tree.
