# Sizing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the four sizing divergences this repo has deferred for four milestones — root percentages, BM-4, FS-3 and TX-H — each verified against live WebKit by a fixture that was RED before its fix.

**Architecture:** Four independent rule changes in `Sources/MetalUILayout/FlexEngine.swift`, applied in dependency order from most isolated to most entangled. Each is preceded by its own fixture task whose only deliverable is a browser-generated golden that the *current* engine fails. No new modules, no new infrastructure: the oracle harness, the fixture generator and `committedGoldensMatchTheBrowser` already exist.

**Tech Stack:** Swift 6, SwiftPM, `swift-testing`, WebKit via the existing `generateGolden` harness.

**Spec:** `docs/superpowers/specs/2026-08-30-sizing-design.md`

## Global Constraints

- **Baseline:** `master` at `a98bd8a` → branch `feat/sizing` at `66d7e1f`. **741 tests**, **81 goldens**, **29** `swiftc -typecheck` guards, warning-free including `MetalUIDemo`.
- **Read the test summary line, never the exit status.** Run `swift test --no-parallel` unfiltered; `--filter` is a different program and cannot be trusted for a count.
- **A pre-existing golden that moves is a FINDING, not a regeneration.** These fixes change stored sizes, so a moved golden is possible for the first time in several milestones. Chase it to a WebKit comparison and explain it. Regenerating it to make the suite green is the one forbidden response.
- **A new fixture must be RED before its fix.** A fixture green on arrival cannot see the defect — redesign it, do not accept it.
- **A fixture must be able to express its defect.** A box with no content, or whose min-content equals its max-content, can see neither FS-3 nor TX-H. Every new fixture states in its own comment which clause it would fail under.
- **No text fixture may be added** (ruling TX-B). WebKit shapes with its own font stack, so a text golden pins the browser's typography rather than this engine's rule. TX-H's user-visible form is text; its *fixture* must be boxes.
- **`MetalUILayout` may import only `MetalUICore`.** Verify with an anchored pattern — an unanchored `Metal` also matches `import MetalUICore`.
- **Regenerating goldens is deliberate and env-gated:** `METALUI_REGENERATE_GOLDENS=1 swift test --filter regenerateAllGoldens`. A new fixture must also be added to `allFixtures` in `Tests/MetalUILayoutTests/GeneratorTests.swift` with its viewport, or it is never generated and never checked.
- **Mutation discipline:** name the tests each mutation reddens rather than counting them; if you re-measure, re-take the whole table. Anything a mutation teaches must be walked back to the mutated **line** in the same pass.
- **Divergence 4 / ruling CS-I is OUT OF SCOPE and must not be touched.** An `auto` root axis keeps taking the offered extent. Only the root's *percentage* branch changes.

## Task 4: An over-constrained box grows its border box

- Consumes: Task 3's `overConstrainedBoxGrowsLikeWebKit`.
- Produces: nothing later tasks call.

- [ ] **Step 1: Floor each axis at its padding plus border**

`resolveNodeSize`'s inner `axis` function today reads:

```swift
    func axis(_ dim: Dimension, _ minDim: Dimension, _ maxDim: Dimension,
              parentExtent: Double?) -> Double {
        let resolved = resolveDimension(dim, against: parentExtent, rootFontSize: rootFontSize)
        let lower = resolveDimension(minDim, against: parentExtent, rootFontSize: rootFontSize)
        let upper = resolveDimension(maxDim, against: parentExtent, rootFontSize: rootFontSize)
        return clamp(resolved ?? 0, min: lower, max: upper)
    }
```

It must additionally floor the result at the node's own padding + border on that axis. Both resolve against the **containing block's width** on every edge (this repo's own constraint — the vertical edges take the width basis too), which `resolveNodeSize` receives as `parent.width`.

**Decide and record whether the floor applies before or after the min/max clamp**, and verify the choice against WebKit with a throwaway probe: a box whose `max-width` is *smaller* than its padding + border distinguishes them. Do not guess — the two orders give different answers and only one matches.

  /* Ruling FS-3. CSS Sizing §4.5's automatic minimum — what `min-width: auto`
     resolves to, the default on every flex item — is
       min(specified size suggestion, content size suggestion)
     and this engine implements the CONTENT half only.

     `.a` is a container declaring 130px and holding a 200px child, so its
     content suggestion is 200 and its specified suggestion is 130. WebKit
     floors it at min(130, 200) = 130. This engine floors it at 200, cannot
     shrink `.a` at all, and squeezes `.b` to 0.

     WHY 130 AND NOT 100: this is the discriminating width. At `width: 100px`
     WebKit gives a=100 b=50 and this engine a=200 b=0 — a difference, but one
     that a "floor at the declared width" bug also produces. At 130 the answers
     are a=130 b=20, and only min(specified, content) gives them: flooring at
     the content 200 gives 200/0, and NOT flooring at all lets `.a` shrink
     below 130 to 75.

     `.b` IS AN EMPTY DIV and must shrink to 20. Its content suggestion is 0,
     so 0 wins its own `min` and it is not floored at all. That asymmetry is
     what stops a "floor every item at its specified size" bug passing.

     Geometry: 150 = 130 + 20 exactly, so no edge lands on WebKit's 1/64 grid. */

  .a { display: flex; width: 130px; }
  .a > div { width: 200px; height: 20px; }
  .b { width: 100px; height: 20px; }
</style></head><body>

## Task 6: The automatic minimum takes the specified size suggestion

**Files:**
- Modify: `Sources/MetalUILayout/FlexEngine.swift` (`collectItems`' `minMain`)
- Modify: `Tests/MetalUILayoutTests/FlexEngineTests.swift` (invert the pin)

**Interfaces:**
- Consumes: Task 5's `specifiedSizeSuggestionMatchesWebKit`.
- Produces: an item's floor is now `min(specified, content)` — Task 8's `ownCross` runs against main sizes this changes.

- [ ] **Step 1: Take the `min` of the two suggestions**

`collectItems`' `minMain` today returns the content suggestion alone:

```swift
                    let probe = measureNode(ctx, tree, kid, known: .unspecified,
                                            available: AvailableSpaceSize(
                                                width: isRow ? .minContent : .maxContent,
                                                height: isRow ? .maxContent : .minContent),
                                            containingBlockWidth: containerSize.width)
                    return isRow ? probe.width : probe.height
```

Replace the `return` with `min(specified suggestion, content suggestion)`, where the **specified size suggestion is the item's own definite main size** — its declared `width` (row) or `height` (column), resolved against the container's main extent — and is absent when that axis is `auto`, in which case the content suggestion stands alone.

**`known: .unspecified` on the probe must stay.** The comment above it explains why: handing the item's own size down as `known` would silently substitute the specified suggestion *for* the content one instead of taking the `min` of both. That comment is correct and becomes more load-bearing after this change, not less.
