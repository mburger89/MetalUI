# Code view - decisions (prefix `CV-`)

Rulings for Alloy gap G1, a code view (Alloy is an LLM-first code editor targeting Zed-level typing latency and scroll frame times). Plan: four PRs, `MetalUICodeBuffer` first. Branch `feat/code-buffer` from master `4d4c59db`; record 225. Class `M` (MetalUI-only): no divergence added or retired (labels untouched). **Next unused id: `CV-AU`.** `CV-A`..`CV-I` are PR 1, the buffer module (record 225); `CV-J`..`CV-R` are PR 2 run 1, the read-only `CodeView` (record 227, branch `feat/code-view`); `CV-S`..`CV-V` are PR 2 run 2 (virtual rows, scroll sync, the accessibility node, allocation rules, same record); `CV-W`..`CV-Z` are PR 3 run 1, editing (record 228, branch `feat/code-edit`); IME, the caret blink, drag autoscroll, the gutter-bar callbacks and find painting append their own rulings. Public API (PR 1): `CodeBuffer`, `CodeSnapshot`, `CodeEditCursor`, `CodeEdit`, `CodeEditBatch`, `CodeEditOrigin`, `CodeTextEdit`, `CodeSelection`, `CodePoint`, `CodeTransactionID`, `CodeBufferError`, `CodeBias`, `CodeLineEnding`, `CodeFindOptions`. No guide in PR 1 (a guide needs compiled mirrors in `MetalUITestingTests`); usage is in `docs/api-overview.md` and record 225.

## CV-A: a pure portable target that imports only Observation

`MetalUICodeBuffer` is in the portable manifest list (`PC-A`), imports **only `Observation`** (no Foundation, no `MetalUICore`), has its own library product so an app (Alloy's `AlloyKit`) can use the buffer without any UI, and `MetalUI/App.swift` re-exports it (`@_exported import MetalUICodeBuffer`). `Observation` ships with the toolchain on Linux and Windows and `MetalUI` already imports it there; `@Observable` in a Foundation-free module compiles on all three (Linux container run, record 225 section 4). Its tests (`MetalUICodeBufferTests`) are in the portable list, so `scene-linux` and `root-windows` build and run them with no workflow change (`swift build --build-tests` / `swift test --no-parallel` run every declared target). Foundation-free also means no `String(format:)`, no `Date`, no regex; the code uses `UTF8` decoding from the standard library only.

## CV-B: the rope

A persistent B-tree over UTF-8 chunks. Node: final class, `height` (0 = leaf), a `ContiguousArray<Chunk>` (leaf) or `ContiguousArray<Node>` (inner), and a cached `Summary`. **Branching 16 maximum, 12 fill** (a split or a build makes groups of about 12; two neighbours merge after a deletion when they fit 12). **Chunk 768 bytes maximum, 512 target, neighbours merged when they fit 512.** (The plan said 64-256 bytes; with a 14-byte summary, a 24-byte slot and a 32-byte array header per chunk that is 0.3 or more of the text, over the 1.3x budget. 512 gives 1.14.) A chunk never starts inside a scalar and never starts between the `\r` and `\n` of a CRLF: `chunkify` moves a cut forward past continuation bytes and past an `\n` that follows `\r`, and `fixCRLF` repairs the one place an edit can recreate the split (a deletion that joins a chunk ending in `\r` to one starting with `\n`). Chunk arrays are built at exact size and never mutated, so a chunk is shared freely between snapshots. **Summary** per subtree: bytes, UTF-16 units, scalars, newlines, first line (scalars), last line (scalars and bytes) and longest line (scalars); two summaries combine without the text. A chunk stores it as seven `UInt16` (`ChunkSummary`, 14 bytes), which fit because a chunk is at most 768 bytes. **Copy-on-write**: every mutation passes `Rope.unique(_:)`, which copies a node that another reference holds (`isKnownUniquelyReferenced`); a node reachable from a snapshot is never mutated, so `Node` is `@unchecked Sendable` and a snapshot is O(1) and `Sendable`. A deletion drops whole children it covers without entering them (O(depth) plus children removed); an insertion rechunks the one chunk it lands in and splits upward. **Row lookup needs no line index**: row to offset descends the newline counts. **Memory** is judged by arithmetic over the nodes (`Rope.storageBytes`: object headers, array headers, slots, chunk payload at its byte count), not malloc: 1.14 built and at most 1.17 after thousands of random edits (pinned at 1.3). **Work is counted, never timed**: `RopeStats.nodesVisited` (a raw-pointer counter, so concurrent snapshot readers cannot trip exclusivity checking) counts nodes a rope operation enters; the build counts the nodes it creates.

## CV-C: UTF-8 byte offsets everywhere

The rope's storage and Swift's native encoding, so slicing a chunk to a `String` needs no transcoding; tree-sitter's `TSInputEdit` is bytes plus (row, byte-column) points. Every other unit is one summary descent away: `scalarOffset(ofUTF8:)`, `utf8Offset(ofScalar:)`, `utf16Offset(ofUTF8:)` and `utf8Offset(ofUTF16:)` (the last two for a future `NSRange` boundary), `point(at:)`, `offset(of:)`. Carets snap to grapheme boundaries in the view (PR 2+), computed on the line's `String`; graphemes are not stable under edits and are not summarized. A line is a run between `\n` bytes; `line(_:)` and `lineRange(_:)` exclude the terminator (`\n` or `\r\n`), while a lone `\r` at the end of the last line stays content. A `CodePoint` column is in bytes. Alloy's review accepted these units (the plan's addendum, Q1).

## CV-D: edits, events and selections

`replace(_:with:origin:)` is one event; `transaction { }` groups events under one id and one undo step; `replaceSelections(with:origin:)` is the typing primitive (every selection replaced, a caret left after each, one transaction when there are several, coalescing when there is one). **Each `CodeEdit` is in the coordinates of the text just before it**, with `range`, `scalarRange`, `startPoint`, `oldEndPoint` (from the OLD text) and `newEndPoint`; computing them costs two prefix descents. **A multi-range edit applies highest range first**, so every event's coordinates are also the transaction's original ones; edits at one offset insert in array order, and a replacement sorts before an insertion at its own start. **`version` rises by exactly 1 per event** and is never reused. **Selections move eagerly on every event**: before the span unchanged, after it shifted, inside it `start + min(offset - start, newLength)` (an offset keeps its distance into a same-size hunk); an offset at the point of a pure insertion stays in front of the text unless the origin is `.typing` or `.paste`, which moves it after the text. The array is kept sorted and merged (overlapping selections and coinciding carets become one) and clamped. Assigning `selections` or calling `select(_:reveal:)` ends undo coalescing; the buffer's own movement of selections does not. `revealSerial` rises only when `reveal` is true. `isReadOnly` makes `replace` and `transaction` do nothing and the external entry points throw `.readOnly`. A range outside the text or inside a scalar is a programming error in `replace` (precondition) and a thrown `.invalidRange` in the external entry points, which validate everything before applying anything.

## CV-E: the edit stream is pulled through cursors

`makeEditCursor()` returns a `CodeEditCursor` (held weakly by the buffer); `drain()` returns `.edits([CodeEdit])` since its last drain, or `.resync(CodeSnapshot)` when the log no longer reaches back that far. The log is kept back to the slowest live cursor, with a floor of the latest 256 events (`editLogMinimumEvents`) so `map` works with no cursor alive, and capped at 4 MB of inserted text (`editLogByteLimit`; the cap wins over cursors). `version` is observable, so a consumer wakes on change and drains. `map(_:from:bias:)` carries an offset through the retained log and is `nil` when the log was trimmed or the version is from the future; at an insertion point `bias` decides, inside replaced text it collapses to the replacement's start (`.before`) or end (`.after`). Composition (IME marked text) never enters the buffer or the stream until committed (the view's rule, PR 3).

## CV-F: undo and external edits

**Undo is operation-based**: a group stores the inverse steps (a range in the text just after the step, and the text it held) and the selections to restore on either side. Typing coalesces when the next step's removal starts where the previous one ended (the pair becomes one replacement); backspace and forward delete each merge into one reinsertion; a caret move, a selection write, `breakUndoCoalescing()`, a transaction, undo/redo and an external edit end the run; no time-based grouping (tests never sleep). Depth is capped by bytes (`undoByteLimit`, 8 MiB; the oldest steps go first). Undo and redo apply the stored steps last to first as ordinary events with origin `.undo(id)` / `.redo(id)`, `id` being the group's first transaction, and a fresh transaction id; the events they produce become the opposite stack's group, so the same group moves between stacks. **External edits** (`applyExternalEdits(_:expectingVersion:)`) are one transaction with origin `.external`, off the undo stack. `.stale(current:)` when `expectingVersion` differs. The undo and redo stacks are rebased over them: walking each stack from the step that applies first, an inverse step whose range **touches** an external range (closed interval overlap, conservative) is dropped together with every step beneath it (which depends on it); the others shift, and the external ranges are carried through each step into the next step's frame. The stored selections shift approximately (clamped when restored). **`applyExternalReplacement(_:)`** trims the common prefix and suffix back to line starts, runs a Myers line diff on the middle and applies the hunks as above; a middle needing more than 1000 line edits is one hunk (the diff's memory is quadratic in the distance); it is O(n), meant for a reload or `git checkout`, and returns `nil` when nothing differs. Pinned: a small external hunk into 100k lines visits the same number of nodes as into 1k lines, plus the extra tree levels.

## CV-G: opening a file

`CodeBuffer(utf8:)` validates the bytes (a `UTF8` decode loop, no allocation), repairs invalid sequences to U+FFFD via `String(decoding:)` and sets `hadInvalidUTF8` so an app can refuse to save a binary file. It then builds bottom-up from the bytes in one scan, O(n), no per-line objects. `lineEnding` is detected from the first line break (`\r\n` gives `.crlf`, anything else `.lf`); CRLF files are kept verbatim in the tree.

## CV-H: the find engine

`CodeSnapshot.ranges(of:options:limit:)`: a streaming Knuth-Morris-Pratt over the chunks, left to right, non-overlapping. `CodeFindOptions.caseInsensitive` folds ASCII letters only (non-ASCII scalars match exactly); `wholeWord` requires a non-word byte on both sides, where a word byte is an ASCII letter, digit, underscore or any non-ASCII byte. A match always starts and ends on a scalar boundary because the query is valid UTF-8. O(n) per query, run when the query changes, never per frame. Regular expressions and full case folding are out of scope for now. The find bar belongs to the app; painting and navigation are PR 4.

## CV-I: observation and threads

`CodeBuffer` is `@MainActor @Observable`. Observed: `version`, `selections` (a computed property that calls `access`/`withMutation` itself, so the observation does not depend on a property observer), `revealSerial`, `lineEnding`, `isReadOnly`; `utf8Count`, `lineCount`, `snapshot()`, `canUndo`, `canRedo` and `map` register a dependency on `version`. Everything else is `@ObservationIgnored`. Each event writes `version` (one notification per event; a `transaction` notifies once per event inside it). A snapshot is the only thing that crosses threads. Swift 6 mode is on (the package default): the node counter is `nonisolated(unsafe)` plain memory.

## CV-J: the view is one leaf element, and run 1 is read-only

`CodeView(buffer:decorations:)` is a `StyledElement` leaf (the shape of `TextEditor`), not a view per line and not a `GPUSurface`: a keystroke or a scroll then costs the rows it touches, never the document (Alloy's addendum 6). It lowers at the `.textEditor` site (`LoweringSite` gains no case: the diagnostics tables enumerate sites, and the leaf lowers exactly as the editor does). Its modifiers in run 1 are `font(family:size:)` (the system's monospaced face when no family, resolved through `resolveTextStyle` with `monospaced`), `showsLineNumbers(_:)` and `tabWidth(_:)`; `codeViewEditable` and `indentUsingSpaces` belong to the editing run, so they are **not declared** (an unread property is a declared-but-inert row, record 05). Run 1 and run 2 are read-only: it selects with the mouse, copies, scrolls and draws; it takes no `textInput` target, so `Handlers` stays at 488 bytes and no `Window` stage grows an arm. Code ignores the layout direction (the gutter stays on the left). **Display rows are not buffer rows from the start**: `CodeRowMap` is the one place a display row becomes a buffer row or a virtual line (`CV-S`). The class is `M`; no divergence.

## CV-K: decorations follow the buffer in O(log n), and the provider is never called in a phase

`CodeDecorations` is an `@Observable` class that owns, per `CodeHighlightLayer`, a `RunTree` (`RunTree.swift`: a treap of runs addressed by running extent, so a splice at one position is O(log n) in the number of runs, never an array move) of `(style?, state)` over the buffer's bytes, and one `RunTree` of line decorations over its rows. It **follows the buffer itself**: every read first drains its own `CodeEditCursor` (`sync()`, which writes only `@ObservationIgnored` storage, so a phase may call it) and shifts the runs (an edit grows the run it lands in and marks that stretch stale, so typing never flashes unstyled text) and the line decorations (a newline splices rows after the start row; the inserted rows take the decoration of the row before). `setHighlights(_:in:layer:asOf:)` maps its runs and range from `version` to now through `CodeBuffer.map` (start `.after`, end `.before`) and drops a run the log no longer reaches; `setLineDecorations(_:asOf:)` builds the tree at the rows of `version` and replays the recorded row deltas since (4096 kept; older is dropped). **The provider** (`CodeHighlightProvider`) is asked, once, for the contiguous span of unknown or stale rows within the viewport and one viewport each side; the view queues the call as a `LifecycleEvent` (`LifecycleStore.enqueue`) that `Window.drainLifecycle` runs after the build, outside every phase and under `StateDispatch`, so its `setHighlights` is an ordinary observed write. It is not asked again for the same rows at the same buffer version and decorations revision; `invalidateHighlights` re-arms it. Only the observed stamp `revision` and `theme` redraw; the lazy drain bumps nothing. Pinned by `lineDecorationsShiftInLogarithmicWork` (`RunTreeStats.nodesVisited`, 1k against 100k rows), `highlightsGivenForAnOlderVersionAreMappedForward`, `theProviderIsAskedOnceAfterTheFrameAndItsAnswerColoursTheText`.

## CV-L: styles are colour only; the layers are ordered, annotations sit under syntax

A `CodeStyle` is a foreground and a background `Color?` (a weight or slope would change where glyphs go, so v1 has neither). `register(_:)` interns equal styles. `CodeHighlightLayer` is `annotations`, `syntax`, `semantic`, `diagnostics` in drawing order: **a later layer's foreground wins**, backgrounds are painted in layer order, so an authorship tint from the app (`annotations`) is under every syntax colour (Alloy's addendum 3). `CodeTheme` holds only what run 1 draws: `foreground`, `background`, `selection`, `gutterForeground`, `gutterBackground` (the current-line, caret and find colours arrive with the runs that paint them). A theme change re-resolves colours at paint and re-shapes nothing.

## CV-M: the line-layout cache holds keys, never slots, and is an idempotent memo

One entry per distinct line **content**: a 64-bit FNV hash of the line's bytes and their count (never a `String`), a digest of the foreground partition, the `FontKey`, the scale's bit pattern, the tab width, the text system's identity and a long line's byte window. The value is origin-free: `[TextGlyph]` at pixel offsets from the line's top-left, the part (colour run) of each glyph, and the grapheme boundaries with their x; a hit is placed by a **whole-device-pixel** translation, which is exact because every row origin, segment origin and scroll offset is a whole pixel. It stores glyph keys and never atlas slots, so the atlas reclaim (`GL-A`) and the flattening re-key (`TZ-A`) have nothing to invalidate; it is a function of its key, so a redone build or a replayed frame loses nothing and **no `rollbackBuild` is owed**. Two frames: `begin(_:)` rotates current into previous when the frame changes (a weak reference to the last frame); a line touched in neither is dropped. Shaping goes through `layOut(StyledText(keepingNeighbours:runs:))`, one run per foreground part in one face, so the glyphs match plain placement. **Tabs** are never passed to the text system (the two systems answer a control differently): a line is cut at `\t`, each segment shaped alone and placed at a whole-pixel origin, and a tab advances the pen to the next multiple of `tabWidth` space advances **from the pen's real end**, never from a glyph count. **A line over 4096 bytes is shaped as a column window** (the visible columns, 256 each side, rounded to multiples of 256, columns estimated from the space advance): only the window's bytes are shaped and the window is in the key; for a proportional face the estimate is approximate (a named limit), and a position outside the window clamps to its edge. `METALUI_VERIFY_CODE_CACHE=1` re-lays every hit fresh and traps if the glyphs, parts, boundaries or caret x differ.

## CV-N: geometry in whole device pixels, a leaf that measures nothing of the buffer, one plan per frame

The line pitch is `round(lineHeight * scale)` device pixels (Windows' 1.25 and 1.5 included), every row's top, the gutter, the padding and the horizontal offset are integers, and rects are emitted as `pixels / scale`. **The leaf's measure is a function of the proposal alone** (greedy on both axes, 480 by 320 on a nil axis) and its key `CodeViewLeafKey` is empty, so a keystroke, a scroll or a highlight re-lays-out no ancestor (pinned: `aKeystrokeInTheBufferRelaysOutNothing`, zero measure calls and zero memo misses; and a "key covers the closure" test). Prepaint builds one `CodeViewPlan` (a class, kept in `Layout` for paint and held by the pointer handlers of that frame): the pitch, the origin and gutter, the clamped scroll, the visible display rows plus one of overscan each side, each row's cached layout and styling, and the gutter labels (shaped through the same cache, counted apart). The view paints, in order: the view fill, the gutter fill, line tints (consecutive equal rows are one rect), run backgrounds, the selection (with the line break's 4-point tail), the glyphs, the gutter numbers, the author bars, then both scroll indicators. Row culling is by the viewport, so overscan rows are shaped and not painted.

## CV-O: the view scrolls itself; the anchor is a byte offset; writes are compared

`CodeViewState` (Equatable, in the `StateTable`) holds the **scroll anchor as a byte offset and the buffer version it was taken at**, the device pixels scrolled into the anchor row, the horizontal offset, pending wheel travel (points), the widest line laid out so far and the last wheel time. Prepaint maps the anchor through `CodeBuffer.map(_:from:bias: .before)` (so text inserted at the anchor stays in view and lines inserted above leave the reader where they are), folds the pending travel, clamps both axes and writes the result back through a **compared** `withState(…unchanged: ==)`: a settled view bumps no version, a changed one converges in one frame (`TextEditor`'s precedent). The wheel is the pointer attachment's `scrollWheel` handler (the existing hook, so `Handlers` and the `Window` scroll chain gain nothing): it accumulates clamped travel in state **from input**, never from a phase. The horizontal extent is the longest line's scalar count times the space advance, **corrected upward by the widest line actually laid out** (a row of wide glyphs the estimate calls narrow scrolls to its real end). Shared arithmetic: `ScrollChrome.wheelOffset(x:y:delta:maximum:)` (natural scrolling, per-axis clamp; the `TextEditor` arm in `dispatchScrollChain` now calls it) and `ScrollChrome.paintIndicator(bounds:offset:content:viewport:lastScroll:pass:)`, the indicator from numbers instead of a content node and a `ScrollState` (the old method forwards to it), one call per axis. `select(_:reveal: true)` centres the head's row (`revealSerial` seen in state; the first frame honours none).

## CV-P: selection and copy

The selection is the buffer's primary selection (shared by every view of the buffer). A drag (`DragGesture(minimumDistance: 0)`) selects by character; a double click by word (`TextEditing.isWordCharacter`, a whitespace run, or one symbol) and a triple click or a press in the gutter by line (the break included), extending by the same unit while dragging; the hit test is the plan of the frame the handler was registered in (view-local points to a grapheme boundary through the line's caret x). The view is focusable with `.edit` interactions (a primary press focuses it, as a canvas or text field), and `copyable` supplies the clipboard handler: the selection as plain text, nothing for an empty selection. No caret is drawn in run 1.

## CV-Q: counted work

`FrameWork` gains `codeLinesShaped` (a miss in both frames of the cache), `codeLinesPainted` (rows intersecting the viewport), `codeGlyphsEmitted` and `codeHighlightRunsVisited`, carried `Frame.codeWork` -> `BuildWork` -> `FrameWork` (`TestingHooks`, `TestApp`). Every performance pin of the view counts these, `RunTreeStats.nodesVisited` or heap allocations (`countAllocations`, Darwin); none reads a clock.

## CV-R: rope scans use buffer pointers and `while` loops

`Rope.lineStart(row:)`, `utf8Offset(ofScalar:)` and `utf8Offset(ofUTF16:)` scanned a chunk with `for i in 0..<ch.count where ch.bytes[i] == ...`, which allocated once per byte (511 allocations for one `lineStart` at row 600 of a 1k-line buffer, found by the view's allocation pin). They now scan the chunk through `withUnsafeBufferPointer` in a `while` loop (11). A hot scan over a chunk's bytes does not use the `for ... where` spelling over an array element.

## CV-R (amended, run 2): the allocation rules of a hot path in a debug build

Run 2 measured where a warm scroll frame's heap allocations come from (a `malloc_logger` that records the backtrace of every allocation on the test thread, aggregated by the first MetalUI frame; the scratch instrument is not kept). **Nearly all of the 4380 were not the view's own work but the debug build's unspecialised generics**: a `for x in array`, `for i in 0..<n`, `.enumerated()`, `.last`, `.contains`, `reduce` and `filter` call a protocol witness (`IndexingIterator.next`, `Collection.subscript.read`, `BidirectionalCollection.last`) that allocates a coroutine frame **once per element**, and `-Onone` does not specialise them. Release builds specialise them away, so the pin is a debug-build pin, and the rule is: **a loop on a per-frame path over a per-glyph, per-row or per-byte collection is a `while` over an index, a last element is `a[a.count - 1]`, a product is a loop**. Applied to the view's paint loops, `codeHash` (a buffer pointer), `stylingOfLine` (no tree walk and no scratch arrays when no layer holds a styled run, `layerHasStyles`), the gutter labels (a per-number two-frame cache, `CodeLineCache.number`), `Rope.lineStart`/`byte(at:)`/`forEachSlice`, and the two shared hot spots every glyph passes through: `Frame.activeClip`/`activeClipRadii`/`activeOffset`/`activeOpacity` (read once per glyph in `spriteGlyph`) and `Scene.finalize` (its fill loops and run merge). Measured, one warm 1 px scroll frame of 12 rows, numbers off, debug: 4380 / 4522 at the top (1k / 100k lines) and 5040 / 5077 at 600 rows before; **764 / 764 at the top, 777 / 778 at 600 rows and 750 at 90 000 after** (an empty view's frame is 157 of them; of the 764, about 400 are `Scene.finalize`'s sort of the frame's primitives, which scales with the glyphs on screen and not with the view).

## CV-S: virtual rows are a treap of gaps in the row map, anchored to buffer rows and mapped like line decorations

`CodeDecorations.setVirtualRows(_:asOf:)` takes `CodeVirtualRow`s: lines of text that are **not** buffer text, shown between buffer rows (the removed lines of an inline diff, a note, or blank **filler** that aligns the two sides of a side-by-side diff). `CodeRowMap` is a treap over *gaps*: a node is a group of virtual lines anchored before a buffer row (`.after(line: n)` is the gap `n + 1`), its `extent` the buffer rows since the previous gap and its `height` the group's line count, so the subtree sums answer **display row to buffer row or virtual line** (`row(atDisplay:)`) and **buffer row to display row** (`displayRow(ofBufferRow:)`) in O(log n) in the number of groups; the view's geometry (pitch, anchor, extent, reveal, rows) all go through them. **Edits follow like line decorations** (`CV-K`): an edit that adds or removes rows `p..` calls `splice(at:removing:inserting:)`, which splits by gap position and bumps the first later node's extent, O(log n); a gap at the edit's row or before stays in front of the new rows; **a gap strictly inside rows an edit removes is dropped with them** (the app gives the rows again after such an edit; a gap at the end of a removed span moves to its start). `asOf` rows are placed at the rows of that version and replayed through the recorded row deltas (the same 4096 as the line decorations, dropped when the log no longer reaches). A virtual line **is not selectable, copyable or editable and has no line number**: a press on it resolves to the start of the buffer row it sits before (the end of the text when it sits after the last row), a selection paints on buffer rows only, and copy reads the buffer. It may carry a style run per line (`CodeStyleRun`s against that line's bytes; colour only, `CV-L`), a gutter bar, a tint across the row and a gutter marker (`CodeGutterMarker`: text and colour, drawn where the number would be). It is shaped through the same two-frame line cache as buffer lines (its hash is computed once when set), so **open with 10 000 virtual groups shapes only the visible rows**, and a scroll of one row shapes the one that entered. The scroll anchor stays a buffer row plus device pixels, which may be negative when the view's top is inside the virtual lines before it. The accessibility value includes the visible virtual lines in display order. Pinned by `virtualRowsTakeDisplayRowsAndNotBufferRows`, `aVirtualRowCannotBeSelected`, `scrollingAndRevealGoThroughTheRowMap`, `anEditAboveKeepsVirtualRowsWithTheirRowAndTheReaderInPlace`, `virtualRowsGivenForAnOlderVersionAreMappedForward`, `fillerRowsAlignTwoViews`, `aNewlineAboveManyVirtualRowsShiftsThemInLogarithmicWork` (1 newline above 100 and 10 000 groups: the node counts differ by a constant) and `openingWithTenThousandVirtualGroupsShapesOnlyTheVisibleRows`, and by a randomized comparison of the map against an array model (`CodeRowMapTests`).

## CV-T: the scroll position is in display rows; an assignment is adopted and never reported back

`CodeScrollPosition` is `(row: Double, x: Double)`: a **display row plus the fraction of it scrolled off**, and the horizontal offset in points. Vertical is in rows and not pixels because two views of one diff have the same display rows (the filler makes them equal) but may differ in font size, scale or pitch rounding, where a pixel offset drifts apart at the first difference; a row position names the same place in both. `CodeScrollState` is an `@Observable` class: `position` is observed and settable, and the view shares one with `CodeView.scrollState(_:)`. After a frame in which the view's position differs from what it last reported (a wheel, a clamp, an edit above that moved the reader's row), the view queues an event (`LifecycleStore.enqueue`, the provider's mechanism, `CV-K`) that runs after the build, **outside every phase**, and publishes the position to the state and calls `onScroll`. An **assignment** to `position` bumps a revision the view observes; the view adopts the value on its next frame (before that frame's wheel travel, which it drops) and publishes the clamped result **without** calling `onScroll`, so two views each setting the other's `position` from `onScroll` settle after one hop and never echo (pinned: `twoViewsSyncedThroughOnScrollShowNoFeedbackLoop`, each callback runs once for the view that was wheeled and never for the one that was assigned). The first frame adopts the state's initial value silently. The view's own reports never wake it (it observes the revision only), so there is no redraw loop. Horizontal sync is the same path (`theHorizontalOffsetIsSyncedToo`). A view with neither a state nor `onScroll` reports nothing and queues nothing. The state is the only API; the wheel still arrives through the pointer attachment (`CV-O`).

## CV-U: one `.textArea` node whose value is the visible rows' text

The view declares one accessibility node, `fillControl(role: .textArea, label: nil, value:)`, whose value is the text of the rows in the viewport (virtual lines included), one per line, **capped at 64 KB** on a scalar boundary, **built only while a client is active** (`Frame.collectsAccessibility`; counted by `CodeViewStats.accessibilityTextBuilds`, 0 for a window with no client). It is never the whole document. `AccessibilityNode` has no selected-range or line-for-index field and adding one needs a row on both bridges, so a screen reader reads the visible text and not the selection: a named limit for the human checks (group CV). Pinned by `theAccessibilityNodeCarriesTheVisibleRowsCapped`.

## CV-V: reveal centres the head's display row in every view; the anchor is documented

`CodeBuffer.select(_:reveal: true)` bumps `revealSerial`; **every `CodeView` showing the buffer** sees the new serial in its next prepaint and sets its top so the head's display row is centred: `top = row(head) * pitch - (viewportHeight - pitch) / 2`, then clamped to the scroll extent (so near either end the row is not centred and the viewport sits at the end). The first frame of a view honours no reveal (it starts at the top). The row is the display row, so virtual lines above it count. It is a compared write of the view's own state, not a command, so a view that appears later does not replay an old reveal. ## CV-AI: a rope chunk aims at 472 bytes so header plus payload fills a malloc size class

## CV-AN: the squiggle is one stroked path per run, its geometry a function of the period count and the scale

Alloy's answer 6: match Zed, **phase anchored at the line's start so scrolling does not shimmer it**. Dimensions at a 12-point face, all scaling with the font size (`size / 12`) and the scale factor: **period 4 points** (rounded to whole device pixels, at least 2), **amplitude 1.5 points** from the centre line to a crest (3 points peak to peak; at least one device pixel), **1 point thick** (whole device pixels, round joins, butt caps), the wave centred on the face's underline position. The wave is a cubic S-curve between extrema (control points at 0.3642 and 0.6358 of each half period, a sine's best cubic fit), starting at a trough. **Anchoring**: the first period is the one containing the run's first pixel **counted from the line's first column** (`plan.textOriginX`, which carries the horizontal scroll), so two runs on different rows or at different columns draw the same wave where they overlap and a horizontal scroll moves the wave with the text; the path covers whole periods from that boundary to the one at or past the run's end and the run is **cut by a clip** to its exact extent. Every coordinate is a whole device pixel (the period is an integer, the origin an integer), so the path a run needs is the same path translated by whole pixels when the view scrolls: the CPU raster cache (`GX-B`, keyed in canonical device coordinates, `PF-A`) hits, and a scrolled frame rasterizes nothing (`aSquiggleIsCachedAcrossAScroll`, 1x and 2x).
