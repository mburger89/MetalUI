## PG-A - `trimmedPath(from:to:)` measures true arc length across all subpaths; `Shape.trim` is `TrimmedShape`

**Question.** How does SwiftUI parametrise the fractions: Bézier parameter, per element, per subpath or true arc length? What happens to a closed subpath, a reversed range, an out-of-range fraction, several subpaths?
**Ruling.** Probe TR2 (a 10-long then a 90-long line, 0...0.5 ends at (10, 40), not at an element midpoint), TR3 (a quarter circle's half is the arc-length midpoint (70.711, 70.711), not the parameter midpoint), TR4 (two subpaths of 10 and 90: 0...0.5 is the first whole and 40 of the second, one fraction across all), TR5/TR6b (a closed subpath's closing edge counts, 0.9...1 of a square is (0,4)->(0,0); an explicit triangle's 0.9 lands on (2.414, 2.414)), TR5b/TR6c (0...1 keeps the subpath and its close), TR5c/TR5d (from > to and from == to are empty), TR5e/TR5f (fractions clamp to 0...1), TR7 (empty). `MetalUIPath` implements exactly that (`PathGeometry.trimmed(from:to:)`); a trimmed Bézier stays a Bézier of its degree (de Casteljau). `Path.trimmedPath(from:to:)` wraps it; `Shape.trim(from:to:)` returns `TrimmedShape<Self>` (SwiftUI's `_TrimmedShape`), whose `path(in:)` is the base's trimmed and which lays out as its base. NaN is empty. Fractions are `Double` (SwiftUI's `CGFloat`; a literal compiles the same).

## PG-B - `strokedPath` reuses the stroker and returns closed polygons

**Question.** Does `MetalUIPath` have a stroker to reuse, and how does its output compare with SwiftUI's `strokedPath`?
**Ruling.** `Stroker.stroke` (`GX-E`) already produces the outline polygons the rasterizer fills nonzero; `PathGeometry.stroked(_:tolerance:)` flattens (tolerance `Path.hitTolerance`, 0.01 path units, the hit test's) and wraps each outline in `move`/`line`/`close`. The result fills and hit-tests (`contains`, nonzero) as the stroke draws: probe SP ring samples (50,2), (50,-2) inside, (50,8), (50,12), centre outside; SP dash (2,0) in, (6,0) out; X8 a closed rectangle's band. A closed subpath is two loops of opposite winding; the inner side runs through the vertex (the stroker's pivot, `GX-E`), so **an outline's signed area is not the band's area** - only coverage is, and the tests measure coverage. Differences from SwiftUI (divergence 946): curves, round joins and caps are polylines within 0.01 where SwiftUI's carry curves (SP round: `C` elements), and a width <= 0 is an empty path where SwiftUI's is a zero-area polygon (SP w0). SwiftUI's miter tip for a 90-degree V of width 4 is (10, 12.828) (probe SP V elements; `boundingRect` is not tight there), which the stroker's matches.

## PG-C - Arc length is Simpson on the exact speed, in `MetalUIPath`'s arithmetic

**Question.** How is a curve's length and its distance-to-parameter map computed without libm and bit-identically?
**Ruling.** Each segment is cut into 64 uniform parameter intervals; each interval's length is Simpson's rule on the exact speed |B'(t)| (`+ - * /` and one `squareRoot()` per sample); the cumulative table gives a distance's parameter by 4-point Neville interpolation of t(s). Chord sums with Richardson extrapolation were tried first and measured: the cumulative chord error is curvature-dependent, so a mid-curve fraction was 3e-4 off the true point (a quadratic) - Simpson's table is within 1e-4 of an independent 1e-7 flattening oracle at every pinned fraction and within a relative 1e-7 in length. A line is exact. The code uses no libm, no Foundation and no fused multiply-add; `trimmedPathIsBitIdenticalEverywhere` pins the quarter circle's length and a trimmed end point to the bit, and runs in the portable tests (Linux/Windows CI).

## PG-D - `addRelativeArc` is an unclamped signed sweep

**Question.** What is `addRelativeArc(center:radius:startAngle:delta:)`'s direction and range?
**Ruling.** Probe AR1/AR2: a positive `delta` is the positive angle direction (the same as `addArc(clockwise: false)`; 0 -> +90 about (50,50) r50 ends (50,100)), a negative one the other way. AR4/X5/X6: the sweep is **not** capped at one turn (450 degrees ends at 90 degrees; 1000 at 280; -450 at (50, 0)), where `addArc(center:...clockwise:)` caps at a turn. X7: delta 0 is the line (or move) to the start only. X4: after an existing point the arc starts with a line. The cubics are the same at most 90 degrees pieces as `addArc`'s (`GX-C`), so `addRelativeArc(0, +90)` equals `addArc(0, 90, clockwise: false)` element for element (pinned).

## PG-E - `Transform2D` is the public affine map; `transform:` parameters and `applying`

**Question.** `Path`'s `transform:` parameters and `applying` need a public transform type; `CGAffineTransform` cannot cross the portable seam (`GX-C`) and Foundation's `AffineTransform` would collide.
**Ruling.** `Transform2D` (six `Double`s, CoreGraphics' column convention, `.identity`, `init(translationX:y:)`, `init(scaleX:y:)`, `init(rotationAngle:)`, `concatenating`, `translatedBy`, `scaledBy`, `rotated(by:)`, `inverted()`) maps onto `PathAffine`. **Order follows `CGAffineTransform`** (probe AR7): `t.rotated(by:)`/`translatedBy`/`scaledBy` apply the new step **first** and `t` second; `concatenating(other)` applies the receiver first. `Path.applying(_:)` maps every point and control point (exact for Béziers); `transform:` (default `.identity`, which takes the untransformed code path unchanged) is added to `addRect`, `addRects`, `addRoundedRect`, `addEllipse`, `addPath`, both `addArc`s and `addRelativeArc` as SwiftUI has it (probes AR5/AR6/AR9: the connecting line to an arc's start goes from the untransformed current point to the transformed start). A tangent arc under a transform is built in the untransformed space from the inverse-mapped current point, as Core Graphics maps the construction and not the pen; a singular transform draws it as if there were no current point. `offsetBy` already existed. Divergence 945 (the name and the `Double` components).

## PG-F - `trim` animates through the animation store, not `animatableData`

**Question.** SwiftUI's `_TrimmedShape` is `Animatable` over `AnimatablePair<CGFloat, CGFloat>`; MetalUI has no `Animatable` protocol (divergence 169). How does `trim(from: 0, to: progress)` stroke progressively under `withAnimation`?
**Ruling.** A shape may conform to the internal `PaintAnimatedShape`; `ShapeView.paint` and `Shape`'s default `paint` call `shapeForPaint(_:_:pass:)` first, which asks it for itself with this frame's numbers. `TrimmedShape` runs `[startFraction, endFraction]` through `animatedNumbers` at the element's `$anim-layer.trim` key - the recipe the proposal modifiers' numbers and `storedAnimatedColor` already use (first sighting snaps; no transaction snaps; a mid-flight change re-targets with the running velocity; `noteActiveAnimation` keeps the display link; the track drops after a frame that does not paint it). The wrapped base shape gets its own child key, so `trim` of a `trim` animates both. Not a public `animatableData` (divergence 947): a custom `Shape` cannot declare animatable data, as before.

## PG-G - `UnevenRoundedRectangle` is the per-corner rounded rectangle, a path past its limit

**Question.** `UnevenRoundedRectangle` was a "renderer constraint". Can it be a path shape without a new GPU primitive, and what are SwiftUI's radii?
**Ruling.** The existing SDF rounded rectangle already takes four circular radii (`ShapeGeometry.roundedRectangle(_, cornerRadii:)`), so no new primitive and no shader change (`TE-AD` is not engaged): the elliptical corner of the old "constraint" row stays unoffered, the uneven one is built. SwiftUI's radius rule is not the SDF's half-the-shorter-side clamp (probes X1, X2, Y1-Y7, UR2, UR3): a negative radius is 0; on each side, radii whose sum passes the side keep the smaller (if under half) and the larger fills the rest, or both become half the side; a corner takes the smaller of its two sides; so a lone radius 45 on a 100x60 rectangle stays 45 (`RectangleCornerRadii.fitted`, pinned against every probe case; the rule is the same for `.circular` and `.continuous`). **When every fitted radius is at most half the shorter side the shape is the SDF** (fill, `strokeBorder`, `clipShape`, hit testing by corner circles); **a larger one is a `Path`** (CPU raster, `GX-B`), whose `strokeBorder`/`stroke` go through the stroker and which cannot be a clip (divergence 91). `.continuous` is drawn circular (divergence 90). `RectangleCornerRadii` and `UnevenRoundedRectangle` take SwiftUI's labels in `Pixels`; leading is the left edge (a shape does not read the layout direction). The outline is SwiftUI's with its start (`PG-H`).

## PG-H - A built-in shape's outline starts where SwiftUI's does

**Question.** `trim` and dashes begin at the outline's first point; where does SwiftUI start each built-in?
**Ruling.** Probe TS, UR1, X11-X13: `Rectangle` at its top-left corner running right; `RoundedRectangle`, `Capsule` and `UnevenRoundedRectangle` on the right edge at y = (topTrailing + (h - bottomTrailing)) / 2 running down (h/2 when the right corners match); `Circle` and `Ellipse` at the rightmost point running down; all visually clockwise, closed. `Path(ShapeGeometry)` (the default `Shape.path(in:)` and the CPU stroke route) now follows that - it used to start at the top edge's first corner. Zero-radius corners add no curve; an all-zero-radius rounded rectangle is `addRect`'s order (a rectangle). Consequence: a dashed `strokeBorder`/`stroke` of a built-in starts its pattern where SwiftUI's does. An `UnevenRoundedRectangle` with every radius 0 therefore starts top-left, SwiftUI's mid-right (carried; nothing draws differently without `trim`/dashes).
